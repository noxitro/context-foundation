# 設計と、決めたことの理由

PoC の作りと、そう決めた理由をまとめます。数字は、開発に使った PC
(Windows 11、16 コアの CPU、GPU は使わない)で測ったものです。
確度の表記: 【公式】配布元や一次文書で確かめた / 【実測】手元で測った /
【未確認】確かめていない。

## 全体の形

```text
設定(.cf/config.toml)
  └ source(複数): ルートのフォルダ、含める・除く glob
        │ 取り込み(バイナリ・生成物・大きすぎるファイルを除く)
        ▼
     分割(構文の単位・見出しの単位・行)→ passage
        │ それぞれに、外側のスコープとシグネチャを付ける
        ▼
     索引(.cf/index.db。SQLite の 1 ファイル)
        ├ keyword の索引(FTS5、BM25)
        └ 埋め込み(手元で計算。検索は総当たり)
        ▼
     検索: keyword / semantic / hybrid → 順位つきの passage
        ├ コマンド(人が読む形・エージェント向けの形・JSON)
        └ MCP サーバー(search・status)
```

検索だけを提供します。回答を作ること、ファイルを書き換えることは
しません。

## 置き場所と、設定の探し方

- 設定と索引は、作業フォルダの `.cf` に置く。コマンドは、今のフォルダから
  親へさかのぼって、最初に見つかった `.cf/config.toml` を使う。`--config`
  か環境変数 `CF_CONFIG` で、場所を直接渡すこともできる
- source のルートは、作業フォルダの外でもよい(エンジンのソースと、参考に
  するアプリが別の場所にある、など)
- git には頼らない。ファイルの一覧は、フォルダを歩いて作る。除外は、
  フォルダの名前と glob で決める(`.gitignore` は読まない)。索引の後に
  ファイルが変わったかは、大きさと更新日時で見る

## 取り込み

除くもの(数は、理由ごとに索引に残り、`status` に出ます)。

| 理由 | 中身 |
| --- | --- |
| `excluded` | 既定のフォルダ(`.git`・`.svn`・`build`・`bin`・`obj`・`node_modules` など)、生成物によくある名前、設定の `exclude` |
| `not_included` | 既定の拡張子に無い(設定の `include` があれば、それに合わない) |
| `too_large` | `max_file_bytes`(既定 1 MB)を超える |
| `binary` | 先頭に NUL がある、文字として読めない |
| `generated` | 先頭の 2,000 文字に、自動生成の印がある |
| `long_lines` | `max_line_chars`(既定 5,000)を超える行がある(minify したものなど) |

文字コードは、BOM、UTF-8、CP932(Shift_JIS)の順に試します。

## 分割

### コード(C・C++・C#)

tree-sitter で解析して、構文の単位で分けます。

- 関数は 1 つの passage。クラスなどの型は、上限に収まれば 1 つの passage、
  収まらなければ、中のメンバーに下りる。名前空間には、必ず下りる
- 下りた先の passage には、外側のスコープ(`名前空間::クラス`)を付ける。
  クラスの外に書かれたメンバー関数(`T Class::Method()`)も、同じ
  スコープになる
- シグネチャは、宣言の先頭から本体の手前まで(関数の宣言、クラスの継承の
  行など)
- 直前のコメントは、その単位に含める
- 上限を超える関数は、中の文の切れ目で、同じくらいの大きさに分ける。
  どの部分にも、同じスコープとシグネチャを付け、何番目かを記録する
- 短い単位(1 行の宣言、小さな関数)は、同じ入れ物の中の隣とまとめる
- 解析できなかった範囲は、行で分ける。その行数を数えて、`status` に
  割合を出す

マクロの扱い。C・C++ では、次のものを、解析の前に同じ長さの空白に置き
換えます(行と桁は変わりません。passage の本文は元のままです)。

- `class ENGINE_API Foo : public Bar` の `ENGINE_API` のような、型の名前の
  前に置かれた、大文字だけの名前
- 文として単独で置かれた、大文字だけの名前のマクロ呼び出しで、セミコロンの
  無いもの(1 行のものも、何行にもわたるものも)。次が `{` のものは、関数の
  頭として働くので、そのままにする

置き換えないと、文法が崩れて、クラス全体や後ろに続く宣言まで解析できなく
なります。置き換えた行は、短ければ隣の passage に入り、長ければ行で分けた
passage になります。公開されている C++ のゲームエンジンの一部(C・C++ の
約 6,900 ファイル、115 万行)では、行で分けた行の割合は 2.1% でした【実測】。
コードの流儀によって変わるので、実コーパスでは `status` で確かめます。

`status` は、行で分けた行が多いファイルの名前も出します。原因の多くは、
そのコードに独自のマクロです。上のエンジンでは、`new` の代わりに書く
小文字のマクロが 1 つあり、それを使う関数から後ろが、ファイルの終わりまで
解析できなくなる例がありました。設定の `[chunk] attribute_macros` に、
伏せたい名前(正規表現。例: `'\bmynew\b'`)を足すと、そのファイルは構文で
分かれるようになります【実測】。

### 文書とそのほか

- Markdown は、見出しから次の見出しの手前までを 1 つの単位にする。上位の
  見出しを、スコープ(`章 > 節`)として付ける。コードブロックの中の `#` と、
  先頭の front matter は、見出しにしない。短い節は、同じ階層か下の階層の
  隣とまとめる
- そのほかの文字のファイルは、行で分ける(空行の切れ目を優先する)

### 大きさ

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `[chunk] max_bytes` | 1500 | 1 つの passage の上限。超える単位は分ける |
| `[chunk] min_bytes` | 300 | これより短い単位は、隣とまとめる |
| `[chunk] line_window` | 60 | 行で分けるときの、1 つの上限(行) |

大きさは、UTF-8 のバイト数で数えます(英数字は 1 文字 1、日本語は 1 文字
3)。埋め込みモデルが一度に読める量(512 トークン)に、英語のコードでも
日本語の文書でも、だいたい収まるようにするためです。1 行が上限を超える
ときは、その行だけの passage になります(行の途中では切りません)。

## keyword 検索

SQLite の FTS5 で、BM25 の順位を付けます。語は、索引に入れる前に、この
道具が分けます(索引と質問で同じ分け方です)。

- 識別子は、そのままの語と、camelCase・snake_case・数字の境目で分けた語の
  両方を入れる(`GetBufferPool` → getbufferpool、get、buffer、pool)
- 英語の語尾を少しだけそろえる(複数形の s、-ing、-ed、語末の e)
- 日本語は、2 文字ずつの組にする(「描画処理」→ 描画、画処、処理)
- 質問の側では、英語のよくある語と、ひらがなを含む組を落とす。ひらがなを
  含む組は、助詞や語尾がほとんどで、日本語の文書のどこにでも当たるため
- 本文のほかに、スコープ・シグネチャ・定義している名前の欄と、パスの欄を
  持ち、重みを付ける(既定は、本文 1、名前 4、パス 2)

## 意味検索と、埋め込みモデル

埋め込みは、ONNX の形のモデルを onnxruntime で動かして、手元の CPU で計算
します。PyTorch は使いません。外部の API は呼びません。

### 候補

日本語の質問で英語のコードを探せることが必須なので、多言語のモデルから
選びました。CPU で数万の passage を埋め込める大きさで、配布元に ONNX が
あり、利用の条件が緩いものです。下の表は、配布元(Hugging Face)の情報
です【公式。2026-11-16 に確認】。

| モデル | ライセンス | 大きさ(ONNX) | パラメータ・次元 | 入力の上限 |
| --- | --- | --- | --- | --- |
| `intfloat/multilingual-e5-small`(既定) | MIT | 470 MB | 1.18 億・384 | 512 トークン |
| `ibm-granite/granite-embedding-97m-multilingual-r2` | Apache-2.0 | 390 MB | 0.97 億・384 | 32,768 トークン |

- <https://huggingface.co/intfloat/multilingual-e5-small>
- <https://huggingface.co/ibm-granite/granite-embedding-97m-multilingual-r2>

granite は、モデルカードに、日本語を含む 52 言語と、プログラムのコード
(C・C++ を含む)で学習したと書かれています【公式】。e5-small は、多言語の
汎用のモデルです。どちらも、版(リビジョン)と sha256 を固定して取得
します。

見送ったもの【公式の情報だけで判断。動かしていない】:

| モデル | 見送った理由 |
| --- | --- |
| `intfloat/multilingual-e5-base` | 2.8 億パラメータ(ONNX 1.1 GB)。CPU では数倍遅い見込み |
| `BAAI/bge-m3` | ONNX が 2.3 GB。CPU では、さらに遅い見込み |
| `google/embeddinggemma-300m` | 取得に、利用条件への同意が要る |
| `Alibaba-NLP/gte-multilingual-base`、`Qwen/Qwen3-Embedding-0.6B` | 配布元のリポジトリに ONNX が無い |

大きいモデルで日本語の質問がどれだけ良くなるかは、確かめていません
【未確認】。

### 手元での比較

公開されている C++ のゲームエンジンの描画まわり(約 1,300 ファイル、
8,623 passage)に、同じ内容の質問を、日本語・英語・その 2 つをつなげた
もの(エージェントが日本語の質問に英語の語を足して検索する形)で、12 件
ずつ投げました。当たりの判定は、「期待する名前を、パス・スコープ・
シグネチャのどれかに含む passage が出たか」という粗いものです【実測】。

上位 5 件に当たりが出た割合(かっこの中は MRR):

| 質問 | 方法 | e5-small | granite |
| --- | --- | --- | --- |
| 日本語 | keyword | 0.00 | 0.00 |
| 日本語 | semantic | 0.25(0.24) | 0.33(0.28) |
| 日本語 | hybrid | 0.25(0.23) | 0.25(0.24) |
| 英語 | keyword | 0.67(0.47) | 0.67(0.47) |
| 英語 | semantic | 0.83(0.72) | 0.50(0.50) |
| 英語 | hybrid | 0.92(0.72) | 0.50(0.52) |
| 日本語 + 英語 | semantic | 0.67(0.58) | 0.58(0.56) |
| 日本語 + 英語 | hybrid | 0.83(0.81) | 0.58(0.51) |

合成のコーパス(`tests/fixtures`。13 ファイル、日本語の文書を含む。答えの
ある質問 15 件)では、逆に、日本語の質問で granite のほうが良い結果
でした(semantic の上位 5 件: granite 87%、e5-small 73%)【実測】。

埋め込みの速さは、どちらも毎秒 45〜55 passage でした。8,623 passage の
索引づくりは、e5-small で 181 秒、granite で 156 秒です【実測】。

同じ 12 件を、約 8 倍の索引(同じエンジンの、描画と基盤のコード。約 8,000
ファイル、72,876 passage)にも投げました。モデルは e5-small です【実測】。

| 質問 | keyword | semantic | hybrid |
| --- | --- | --- | --- |
| 日本語 | 0.08(0.09) | 0.33(0.31) | 0.33(0.31) |
| 英語 | 0.58(0.47) | 0.92(0.70) | 0.75(0.64) |
| 日本語 + 英語 | 0.58(0.47) | 0.83(0.65) | 0.83(0.76) |

- 索引が 8 倍になっても、日本語に英語の語を足した質問の hybrid は、上位
  5 件の割合(0.83)を保った
- 英語だけの質問では、hybrid が semantic を下回った。keyword の順位が
  混ざるためで、どちらが良いかは質問の形による
- 日本語だけの質問は、ここでも弱い(0.33)

### 決めたこと

- 既定は `intfloat/multilingual-e5-small`。実際のコードでは、英語の質問と、
  日本語に英語の語を足した質問で、はっきり良かった。エージェント経由では、
  エージェントが検索の語を作るので、この形になる
- 日本語だけの質問では、どちらのモデルも弱い(上位 5 件で 0.25〜0.33)。
  そのため、skill には、英語のコードを探すときは英語の語を検索に入れる
  よう書いている
- granite は、差し替えの候補として残す。日本語の文書が多いコーパスでは、
  こちらが良いかもしれない
- 質問が 12 件と 15 件の、粗い比較である。実コーパスで、調整用の質問を
  使って、両方を比べるのがよい

差し替えは、設定で行います。

```toml
[embedding]
model = 'ibm-granite/granite-embedding-97m-multilingual-r2'
```

上の 2 つのほかのモデルを使うときは、ONNX と tokenizer.json を置いた
フォルダを `model_dir` に、取り出し方を `pooling`(`cls` か `mean`)に
書きます。質問と passage の前に付ける文字が要るモデルは、`query_prefix`
と `passage_prefix` に書きます。モデルを変えたら、索引を作り直します
(索引に、作ったときのモデルの名前を残していて、違っていれば keyword に
切り替えて、その旨を知らせます)。

### 速さについて

- 索引づくりの時間は、ほとんどが埋め込みです(上の例で、分割は 3 秒、
  埋め込みは 150〜180 秒)
- スレッドを増やしても、プロセスを分けても、合計の速さはほとんど変わり
  ませんでした(1 プロセスで毎秒 45〜50、3 プロセスで合計 60 ほど)。
  原因は調べきれていません【未確認】。プロセスを分ける設定
  (`[embedding] workers`)はありますが、既定では使いません
- 量子化した ONNX(配布元にあるもの)も、この PC では速くなりません
  でした【実測】
- GPU は使っていません【未確認】

## hybrid

keyword と semantic の順位を、RRF(Reciprocal Rank Fusion。順位の逆数の和)
でまとめます。それぞれ上位 50 件を取り、定数は 60 です。

keyword の側には、重みを掛けます。重みは、質問の語のうち、索引に 1 回
でも出てくる語の割合の平方根です(`[search] hybrid_weighting = 'equal'`
で、重みなしにできます)。日本語の質問で英語のコードを探すときは、keyword
に当たる語がほとんど無く、たまたま当たった 1 語の結果が上位を占めるため
です。

用語の対応表で質問に語を足したときは、足した語と、元の質問の英字の語で
割合を見ます(下の「日本語の質問」)。日本語の質問の 2 文字の組は、英語の
コードにはほとんど無いので、それも数えると、足した語が効かないためです。

reranker は、後段に差し込めます(`[search] reranker = 'モジュール:関数'`)。
既定では使いません。

## 日本語の質問

日本語だけの質問で英語のコードを探すと、keyword には語がほとんど当たらず、
意味検索も弱くなります。日本語に英語の語を足すと、どちらも大きく良くなります
(下の表の「日本語+英語」)。そこで、検索の前に、用語の対応表で質問に英語の
語を足します(`glossary.py`)。

- 既定の対応表(`glossary_ja.tsv`)は、ゲームエンジンとプログラミングの
  一般の語だけ(約 210 語)。「処理」「仕組み」「関数」のように、どのコードに
  も当たる語は入れない。入れると keyword の重みが上がるだけで、順位が乱れた
- 作業フォルダの対応表(`.cf/glossary.tsv`)を先に当てる。エンジンに固有の
  語や、別のエンジンの用語との対応を、チームで書く
- 質問の英字の語が 3 つ以上あるとき(エージェントがすでに英語の語を足した
  とき)は、既定の対応表を当てない。当てると、下の表の「日本語+英語」の
  順位がかえって下がった
- 足した語は、結果の note(`added terms from the glossary: …`)と JSON の
  `added_terms` で知らせる。評価の記録(`runs.jsonl`)には、対応表を使ったか
  と、作業フォルダの対応表のハッシュを残す
- カタカナだけの語は、前後がカタカナでないときだけ当てる(「ロック」を
  「ブロック」に、「ログ」を「ダイアログ」に当てない)。照合の前に、質問と
  語を NFKC でそろえる(半角カナ・全角英数)
- 英語の語は、空白で区切られた、小文字を含む英字の語だけを数える(GPU の
  ような略語や、`std::vector`・`src/render/buffer.cpp` のような名前とパスは
  数えない)
- 対応表の書き方の誤った行は飛ばし、結果の note で場所を知らせる

公開されている C++ のゲームエンジン(O3DE)の索引(約 7 万 passage、モデルは
e5-small)で測りました【実測】。正解は、パス・スコープ・シグネチャに期待する
名前を含む passage という粗い判定です。上位 5 件に正解がある割合
(hit@5)と、上位 10 件の割合(hit@10)です。

| 質問 | 手法 | 対応表なし hit@5 / hit@10 | 対応表あり hit@5 / hit@10 |
| --- | --- | ---: | ---: |
| 描画まわりの 12 問、日本語だけ | keyword | 0.08 / 0.08 | 0.83 / 0.83 |
| 同上 | semantic | 0.33 / 0.33 | 0.67 / 0.75 |
| 同上 | hybrid | 0.33 / 0.33 | 0.67 / 0.83 |
| 同上、日本語+英語 | hybrid | 0.83 / 0.92 | 0.83 / 0.92 |
| 基盤まわりの 10 問、日本語だけ | keyword | 0.10 / 0.10 | 0.50 / 0.50 |
| 同上 | hybrid | 0.70 / 0.80 | 0.80 / 0.90 |
| 合成のコーパスの日本語の 9 問 | hybrid | 0.56 / 0.89 | 0.78 / 1.00 |

- 基盤まわりの 10 問は、対応表を書いた後に作った(対応表に合わせていない)
  問題。ただし、一般の語を外すかどうかは、描画まわりの 12 問と合成の
  コーパスの結果を見て決めたので、その分の偏りはある
- 日本語だけの質問は、対応表があっても、エージェントが英語の語を足した質問
  (0.83)には届かない。そのため、skill は英語の語を足して検索するよう書き、
  対応表は、エージェントが英語にしなかったときと、別のエンジンの用語の対応
  に使う
- 質問の数が少ないので、差は目安。実コーパスで比べて決める

## 保存

外部のサービスを使わない、SQLite の 1 ファイルです。

| 表 | 中身 |
| --- | --- |
| `files` | 索引に入れたファイル(大きさ・更新日時・行数) |
| `chunks` | passage(場所・種類・スコープ・シグネチャ・本文。本文は縮めて持つ) |
| `chunks_fts` | keyword の索引(FTS5。本文は持たない) |
| `vectors` | 埋め込み。passage の順に並べ、4,096 件ごとに 1 行で持つ |
| `meta` | 形式の版、作成日時、統計、かかった時間、埋め込みモデル |

- 埋め込みは、16 ビットの浮動小数で保存する(32 ビットの半分の大きさ)。
  検索のときに 32 ビットに直して、全部の passage との内積を取る(総当たり)
- 途中のファイルに書いて、できあがってから置き換える(下の「差分更新」)
- ベクトル DB は使っていない。約 7 万 passage では、総当たりで足りた
  (下の「規模と時間」)。それより大きい規模で問題になるかは、実コーパスで
  測ってから決める

## 差分更新

索引づくりのほとんどは埋め込みの時間です。そこで、取り込みと分割は毎回
すべてのファイルについてやり直し(約 8,000 ファイルで 36 秒)、埋め込みだけを
前の索引から使い回します。

- 使い回すかどうかは、埋め込みに渡す文そのもの(場所・スコープ・
  シグネチャ・本文)のハッシュで決める。変更の検知に版管理(git など)は
  使わない。ファイルの先頭に行を足して後ろの passage の行番号がずれても、
  文が同じなら使い回す
- 埋め込みの作り方(モデル・版・次元・ONNX のファイルと大きさ・pooling・
  入力の長さ・passage の前置き・保存の形・文の作り方の版)が前の索引と
  違えば、すべて埋め込み直す
- 消えたファイルの passage は、新しい索引に入らない
- `ctxf index --full` で、使い回さずに作り直せる

O3DE の一部(121 ファイル、約 950 passage)で測りました【実測】。

| 場面 | 埋め込んだ passage | 使い回した passage | 時間 |
| --- | ---: | ---: | ---: |
| 最初の索引 | 951 | 0 | 20.4 秒 |
| 何も変えずにもう一度 | 0 | 951 | 1.2 秒 |
| 3 ファイルを変え・1 つ消し・1 つ足した | 4 | 944 | 1.3 秒 |
| 同じコーパスを作り直し(`--full`) | 948 | 0 | 19.2 秒 |

さらに 5 ファイルを変えて差分更新したものと、同じコーパスを作り直した
ものを比べ、passage と埋め込みが 948 件すべて一致し、検索の上位 10 件の
順位も一致しました【実測】。埋め込みの計算は、まとめて計算する相手によって
浮動小数の末尾が変わりうるので、厳密な一致を保証するものではありません。
16 ビットに丸めて保存するので、この計測では差が出ませんでした。

## 規模と時間

公開されている C++ のゲームエンジンの一部で測りました【実測】。16 コアの
CPU で、GPU は使っていません。モデルは e5-small です。大きいほうの
索引づくりは、ほかの作業と並行だったので、単独ならもう少し速いはずです。

| 項目 | 小さい索引 | 大きい索引 |
| --- | ---: | ---: |
| ファイル | 1,345 | 8,069 |
| 行 | 16 万 | 143 万 |
| ソースの大きさ | 6.7 MB | 59.4 MB |
| passage | 8,623 | 72,876 |
| 索引づくり | 181 秒 | 1,888 秒 |
| うち、取り込みと分割 | 3 秒 | 36 秒 |
| うち、埋め込み | 178 秒 | 1,852 秒 |
| 索引の大きさ | 18.2 MB | 134.8 MB |
| 索引づくりのメモリの最大 | 1.37 GB | 1.39 GB |

検索 1 回の時間です。「起動したまま」は、MCP サーバーの形(索引とモデルを
読み込んだ後)、「毎回起動」は、skill の形(コマンドを 1 回ずつ起動し、
出力が出るまで)です。

| 項目 | 小さい索引 | 大きい索引 |
| --- | ---: | ---: |
| 起動したまま keyword(p50 / p95) | 1.6 / 3.1 ms | 3.8 / 10.8 ms |
| 起動したまま semantic(p50 / p95) | 8.8 / 32.7 ms | 8.9 / 10.5 ms |
| 起動したまま hybrid(p50 / p95) | 10.4 / 21.8 ms | 13.9 / 27.8 ms |
| 起動したままの最初の 1 回(読み込み) | 約 1.0 秒 | 約 1.8 秒 |
| 毎回起動 keyword(中央値) | 0.29 秒 | 0.25 秒 |
| 毎回起動 hybrid(中央値) | 1.6 秒 | 2.0 秒 |

- 最初の索引づくりの時間は、passage の数にほぼ比例する(毎秒 40〜50
  passage)。2 回目からは、変わった passage の分だけ(上の「差分更新」)
- 索引の大きさは、ソースの 2.3〜2.7 倍
- 約 7 万 passage では、総当たりの意味検索は 10 ミリ秒ほどで、ほとんどが
  質問の埋め込みの時間。検索時間のしきい値(3 秒)には、どちらの形でも
  収まる
- 毎回起動の形の時間は、ほとんどが、Python の起動と埋め込みモデルの
  読み込み

## 出力

- エージェント向けの形は、英語の短い文面。1 件ごとに、場所
  (`source:path:行-行`)、種類、スコープ、シグネチャ、本文を返す
- 上位の passage は本文ごと、収まらない分は場所だけを返して、全体を
  12,000 バイトに収める(`[search] max_output_bytes`。上限は 18,000)。
  Copilot CLI は、20 KiB を超える道具の結果をモデルに渡さず、ファイルに
  退かせる【公式】
- 索引の後に変わったファイルを指す結果には、印を付ける

## MCP サーバー

- 標準ライブラリだけで、stdio の JSON-RPC を扱う
- ツールは `search`(`query`・`top_k`・`mode`・`source_id`)と `status`
  だけ。書き込みと、索引に無いファイルの読み出しはしない
- 起動したままなので、埋め込みモデルとベクトルを読み込んだまま保てる
- ツールの定義は、使わない回でも毎回モデルに送られるので、短くしている

## プラグインと、Python の置き場

Copilot のプラグインとして入れたとき、プラグインのフォルダは更新のたびに
置き換わります。そのため、Python の依存(約 200 MB)は、プラグインの外の
利用者ごとの置き場に置きます(`ctxf.py`)。

- 入口の `ctxf.py` は標準ライブラリだけで動き、使える python を探して、
  プラグインの `src` のパッケージを動かす。探す順は、環境変数 `CF_PYTHON`、
  隣の `.venv`(リポジトリを取得して `setup.bat` を使う人)、利用者ごとの
  置き場の仮想環境(`ctxf.py setup` が作る)
- 利用者ごとの置き場の仮想環境は、作ったときの依存の一覧のハッシュを
  覚えておく。プラグインを更新して一覧が変わったら、動かさずに「もう一度
  setup を」と知らせる。一覧が同じなら、更新してもそのまま動く
- `setup` は、壊れた仮想環境を作り直し、依存を読み込めることを確かめてから
  覚え書きを書く。同時に 2 つ走らないよう排他する
- hook は仮想環境の python を起動しない(セッションの始まりを遅くしない)。
  何があっても 0 で終わり、セッションを止めない
