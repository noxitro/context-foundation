# 設計と、決めたことの理由

この道具の作りと、そう決めた理由をまとめます。数字は、開発に使った PC
(Windows 11、16 コアの CPU)で測ったものです。断りが無ければ、GPU は
使っていません。
確度の表記: 【公式】配布元や一次文書で確かめた / 【実測】手元で測った /
【未確認】確かめていない。

## 全体の形

```text
設定(.cf/config.toml)
  └ source(複数): ルートのフォルダ、含める・除く glob
        │ 取り込み(バイナリ・生成物・大きすぎるファイルを除く)
        ▼
     分割(構文の単位・見出しの単位・行)→ passage
        │ それぞれに、外側のスコープとシグネチャを付ける
        ▼
     索引(.cf/index.db。SQLite の 1 ファイル)
        ├ keyword の索引(FTS5、BM25)
        └ 埋め込み(手元で計算。検索は総当たり)
        ▼
     検索: keyword / semantic / hybrid → 順位つきの passage
        ├ コマンド(人が読む形・エージェント向けの形・JSON)
        └ MCP サーバー(search・status)
```

検索だけを提供します。回答を作ること、ファイルを書き換えることは
しません。

## 置き場所と、設定の探し方

- 設定と索引は、作業フォルダの `.cf` に置く。コマンドは、今のフォルダから
  親へさかのぼって、最初に見つかった `.cf/config.toml` を使う。`--config`
  か環境変数 `CF_CONFIG` で、場所を直接渡すこともできる
- source のルートは、作業フォルダの外でもよい(エンジンのソースと、参考に
  するアプリが別の場所にある、など)
- 索引は設定ごとに 1 つで、検索は 1 つの索引だけを引く。いくつものリポジトリ
  を横断するときは、1 つの設定に source を並べる(作業フォルダの下の
  ジャンクションを、それぞれ root にするなど)。いくつもの索引をまとめて
  引く仕組みは、まだ無い
- `init` と setup の対話は、渡されたフォルダのリンク・ジャンクションを
  解決せず、字面のまま root に書く(0.4.14 から)。作業フォルダの中なら
  相対パス、外なら絶対パス。字面では外でも、解決すると中にあるとき(作業
  フォルダそのものをリンク越しに渡したなど)は、解決したもの同士の相対
  パスにする(0.4.13 までと同じ)。指示ファイルなどに書いたパスと、検索
  結果の `roots:` の行をそろえるため
- `init` と setup の対話は、渡されたフォルダの 2 段下までにあるフォルダの
  リンク・ジャンクションを探し、それぞれを root にした source を足す
  (0.4.15 から)。索引づくりはリンクをたどらないので、`external` や作業
  フォルダ全体を選んだだけでは、ジャンクションの先が黙って入らないため。
  足さないのは、指す先が渡したフォルダの中のもの(もとの場所で入る)、
  渡したフォルダを含むもの(作業フォルダの外まで広く入れてしまう)、
  ほかと同じ場所を指すもの、足すほかのリンクの先の中を指すもの、既定の
  名前で除くフォルダの中のものとその名前のもの(索引づくりでも数えない)、
  指す先の無いもの(ジャンクションは、先が無くても `is_dir()` が真になる
  ので、確かめる。足すと、索引づくりがルートの無い source で止まる)。探すのを
  2 段までにしたのは、大きなソースの木を init で歩かないため(探すのは
  フォルダの一覧だけで、ファイルは開かない)
- git には頼らない。ファイルの一覧は、フォルダを歩いて作る。除外は、
  フォルダの名前と glob で決める(`.gitignore` は読まない)。索引の後に
  ファイルが変わったかは、大きさと更新日時で見る
- 索引のファイルは、`.cf` の中にだけ置ける(`[index] path` に絶対パスや
  `..` を書くと止まる)。作業フォルダの設定で、外のファイルを索引で上書き
  させないため
- 作業フォルダの設定からは、Python のコードを読み込まない。設定は、取って
  きたリポジトリに入っていることもあるため(0.3.1 まであった `[search]
  reranker` を外した。下の「hybrid」)
- それでも、`.cf` は自分で作るものとして扱う。設定は、作業フォルダの外も
  指せる(`[[source]] root`、`[embedding] model_dir` と `onnx_file`、用語の
  対応表)。外のルートと手で置いたモデルは意図した機能なので、閉じて
  いない。取ってきたリポジトリに `.cf` が入っていたら、使わずに消して
  作り直す。MCP サーバーで外のフォルダを読まないようにするかは、まだ
  決めていない(下の「まだ無いもの」)
- 索引に書かれたパスは、source のルートからの相対パスのはず。絶対パス・
  ドライブつき・UNC・`/` か `\` で始まる・`..` を含むものは、ファイルに
  触れずに「索引の後に変わった」とみなす(仕込まれた索引で、ルートの外の
  ファイルやネットワークの場所を見に行かないため)

## 取り込み

除くもの(数は、理由ごとに索引に残り、`status` に出ます)。

| 理由 | 中身 |
| --- | --- |
| `excluded` | 生成物によくある名前、設定の `exclude` |
| `secret_name` | 秘密を持ちやすい名前(`.env`・鍵・資格情報の設定など。一覧は [readme-ja.md](../readme-ja.md) の「設定ファイル」)。`include` より先に見る |
| `not_included` | 既定の拡張子に無い(設定の `include` があれば、それに合わない) |
| `too_large` | `max_file_bytes`(既定 1 MB)を超える |
| `empty` | 中身が無い |
| `binary` | 先頭の 8 KB に NUL がある |
| `undecodable` | 文字として読めない部分が多い |
| `generated` | 先頭の 2,000 文字のコメントの行に、自動生成の印がある(下) |
| `long_lines` | `max_line_chars`(既定 5,000)を超える行がある(minify したものなど) |
| `unreadable` | 開けない、読めない |
| `symlink_inside` | ファイルのリンクで、指す先が source のルートの中にある(指す先が、もとの場所で取り込まれる) |
| `symlink_outside` | ファイルのリンクで、指す先がどの source のルートの中にも無い |
| `bad_name` | 名前を UTF-8 で表せない(Linux の別の文字コードの名前など) |

フォルダは、名前で除きます(一覧は readme-ja.md の「設定ファイル」)。
除いたフォルダのうち、`build`・`target`・`packages` のようにソースの置き場
にも使われる名前のものは、中の索引に入りうるファイルを名前だけで数えて、
`status` に出します(エージェント向けの `status` にも 1 行)。版管理・
依存物・ビルドの中間物とキャッシュ(`intermediate`・`deriveddatacache`)など、ソースを置かない名前のものは、数え
ません(数えるだけでも時間がかかるため)。数えるのは、名前と拡張子だけを
見て、ファイルは開きません。合成の木(索引に入るファイル 8,000、`build` の
下に 8 万)では、数える分で歩く時間が約 0.7 秒増えました(1 ファイル
あたり 8 マイクロ秒ほど)【実測】。除く名前の一覧そのものは、0.3.1 から
変えていません。

- フォルダのリンク(シンボリックリンク、Windows のジャンクションとマウント
  ポイント)は、たどらない。指す先がルートの中なら、そこは本来の場所で
  取り込まれ、外なら取り込む対象ではなく、輪になっていれば終わらない
  ため。数は `link_dir` として `status` に出る。リンクの先を入れるには、
  そのフォルダ(リンクのパスそのものでもよい)を root にした source を
  足す。ルートそのものはリンクでもたどる。リンクのパスが、ほかの source
  のルートと同じときは、その source の側で取り込み、`link_dir` には
  数えない
- ファイルのリンクは、取り込まない。指す先がルートの中なら `symlink_inside`、
  外なら `symlink_outside` として数える。中を指すものは、指す先が、もとの
  場所で取り込まれる。リンクの名前で読むと、`.env` や `.git` の中を指す
  リンクが、秘密の名前と除くフォルダの決まりをすり抜けるため
- 一覧できないフォルダは `unreadable_dir` として数える
- ほかの source のルートになっているフォルダは、外側の source では歩かない
  (同じファイルを 2 回入れない)。ルートがまったく同じ 2 つの source は、
  そのまま(`include` が違うことがあるため)
- Windows では、`\\?\` の形のパスで歩くので、260 文字を超えるパスの
  ファイルも取り込む
- 生成物の印は、先頭の 2,000 文字のコメントの行だけを見る。文書
  (`.md`・`.markdown`・`.mdx`・`.txt`・`.rst`・`.adoc`)には当てない。
  0.3.1 までは、先頭のどこかに印の語があれば除いていて、手で書いた文書や
  コードを落としていた。印は 3 つに分ける
  - バナーの形(「This file was generated」「File automatically generated
    by」「Generated by」「automatically generated」「autogenerated」
    「このファイルは…自動生成」「これは自動生成」「自動生成ファイル」
    など)は、どのコメントの行でも、書き出しにあれば印。前に飾りの記号と、
    短い前置き(`NOTE:`・`WARNING:`・`CAUTION:`・`IMPORTANT:`・`注意:`・
    `警告:` など)があってもよい。0.3.1 が見ていた形。「Generated by:」
    (後ろにコロン。表の出どころの注記など)は、0.3.1 と同じく印にしない
  - 説明のコメントにもよく出る形(「auto-generated」だけ、「generated
    from / with / using」「code generated」「parser generated by」などの
    `<名詞> generated by`、「this header was generated」、「自動生成され」
    「自動生成した」)は、ファイルの頭のコメントのかたまり(最初のコードの
    行より前。頭で開いたブロックコメントと docstring の中の行も含む)の
    どこかの行の書き出しにあるときだけ印。`<?xml` の行は、かたまりを
    終わらせない
  - 「@generated」「<auto-generated」、大文字の「DO NOT EDIT」は、
    コメントの行のどこにあっても印。小文字の「do not edit」は、同じ行に
    「generated」があるときだけ
- コメントの行の見分け方。頭のかたまりで開いたブロックコメント(`/* */`、
  マークアップの `<!-- -->`、Python の `"""` と `'''`)の中の行は、行の頭に
  記号が無くてもコメントの行として見る。コードの後ろで開いたものは、`*` で
  始まる行だけを見る。`'` は VB の拡張子(`.vb`・`.bas`・`.vbs`・`.cls`・
  `.frm`)、`<!--` はマークアップの拡張子(`.xml`・`.html`・`.xaml`・
  `.natvis`・`.csproj`・`.props` など)のときだけ、コメントの始まりと
  みなす(ほかの言語では、文字列の中の行のことがあるため)
- `#` で始まる行は、ふつうはコメントの行として見る。ただし `#` の後ろが
  `include`・`import`・`if`・`ifdef`・`ifndef`・`elif`・`else`・`endif`・
  `define`・`undef`・`pragma`・`region`・`endregion`・`line`・`error`・
  `warning`・`using`・`nullable` の語の行は、プリプロセッサの行として
  コードの行とみなす(印を見ず、頭のかたまりもそこで終わる)。`#` が
  コメントの始まりのファイル(拡張子が `.py`・`.sh`・`.cmake`・`.yaml`・
  `.yml`・`.toml`・`.ini`・`.cfg`・`.rb`・`.ps1` のものと、名前が
  `Makefile`・`Dockerfile` のもの)だけは、その語の行もコメントの行として
  見る(「# WARNING: This file is auto-generated by …」「# If you change
  this, …」のようなコメントの行のため)。ほかの言語(C 系・シェーダー
  など)では、その語の行はコードの行のまま。その語で始まらない `#` の行
  (Rust の `#[...]` なども)は、どの言語でもコメントの行として見る
- 生成物の判定の限界。頭のコメントのかたまり(docstring も)のどの行でも、
  書き出しが説明にもよく出る形の手書きのファイル(`// Auto-generated ids
  …` で始まるもの、折り返したコメントの続きの行が「generated with …」で
  始まるものなど)は除かれる。0.3.1 では入っていたものもある。
  文字列の中の行がコメントに見えて、そこにバナーの形があるものも除かれる
  (0.3.1 と同じ)。文の途中の「X is generated by Y」は印にしない。どれも、
  `exclude` か `[index] skip_generated = false` で直す。公開のコード
  (9,939 ファイル)で比べると、生成物とみなしたのは、0.3.1 の規則で
  1,130、今の規則で 1,107 ファイルだった【実測】

文字コードは、BOM、UTF-8、CP932(Shift_JIS)の順に試します。どれでも
読めないファイルは、行ごとに UTF-8 と CP932 を試し、どちらでも読めない
行だけを置き換え文字にします(文字コードの記録は `mixed`)。置き換えた
バイトが 8 を超え、かつファイルの 1% を超えるものは、`undecodable` で
除きます。

## 分割

### コード(C・C++・C#)

tree-sitter で解析して、構文の単位で分けます。

- 関数は 1 つの passage。クラスなどの型は、上限に収まれば 1 つの passage、
  収まらなければ、中のメンバーに下りる。名前空間には、必ず下りる
- 下りた先の passage には、外側のスコープ(`名前空間::クラス`)を付ける。
  クラスの外に書かれたメンバー関数(`T Class::Method()`)も、同じ
  スコープになる
- シグネチャは、宣言の先頭から本体の手前まで(関数の宣言、クラスの継承の
  行など)
- 直前のコメントは、その単位に含める
- 上限を超える関数は、中の文の切れ目で、同じくらいの大きさに分ける。
  どの部分にも、同じスコープとシグネチャを付け、何番目かを記録する
- 短い単位(1 行の宣言、小さな関数)は、同じ入れ物の中の隣とまとめる
- 解析できなかった範囲は、行で分ける。その行数を数えて、`status` に
  割合を出す
- 分ける途中で落ちたファイル(深すぎる入れ子など)は、そのファイルだけを
  行で分け直し、索引づくりは続ける。数と例は `status` に出る。else-if の
  連なりは、入れ子の深さで落ちないよう、再帰を使わずにたどる

マクロの扱い。C・C++ では、次のものを、解析の前に同じ長さの空白に置き
換えます(行と桁は変わりません。passage の本文は元のままです)。

- `class ENGINE_API Foo : public Bar` の `ENGINE_API` のような、型の名前の
  前に置かれた、大文字だけの名前
- 文として単独で置かれた、大文字だけの名前のマクロ呼び出しで、セミコロンの
  無いもの(1 行のものも、何行にもわたるものも)。次が `{` のものは、関数の
  頭として働くので、そのままにする

置き換えないと、文法が崩れて、クラス全体や後ろに続く宣言まで解析できなく
なります。置き換えた行は、短ければ隣の passage に入り、長ければ行で分けた
passage になります。公開されている C++ のゲームエンジンの一部(C・C++ の
約 6,900 ファイル、115 万行)では、行で分けた行の割合は 2.1% でした【実測】。
コードの流儀によって変わるので、実コーパスでは `status` で確かめます。

`status` は、行で分けた行が多いファイルの名前も出します。原因の多くは、
そのコードに独自のマクロです。上のエンジンでは、`new` の代わりに書く
小文字のマクロが 1 つあり、それを使う関数から後ろが、ファイルの終わりまで
解析できなくなる例がありました。設定の `[chunk] attribute_macros` に、
伏せたい名前(正規表現。例: `'\bmynew\b'`)を足すと、そのファイルは構文で
分かれるようになります【実測】。

### 文書とそのほか

- Markdown は、見出しから次の見出しの手前までを 1 つの単位にする。上位の
  見出しを、スコープ(`章 > 節`)として付ける。コードブロックの中の `#` と、
  先頭の front matter は、見出しにしない。短い節は、同じ階層か下の階層の
  隣とまとめる
- そのほかの文字のファイルは、行で分ける(空行の切れ目を優先する)

### 大きさ

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `[chunk] max_bytes` | 1500 | 1 つの passage の上限。超える単位は分ける |
| `[chunk] min_bytes` | 300 | これより短い単位は、隣とまとめる |
| `[chunk] line_window` | 60 | 行で分けるときの、1 つの上限(行) |

大きさは、UTF-8 のバイト数で数えます(英数字は 1 文字 1、日本語は 1 文字
3)。埋め込みモデルが一度に読める量(512 トークン)に、英語のコードでも
日本語の文書でも、だいたい収まるようにするためです。1 行が上限を超える
ときは、その行だけの passage になります(行の途中では切りません)。

## keyword 検索

SQLite の FTS5 で、BM25 の順位を付けます。語は、索引に入れる前に、この
道具が分けます(索引と質問で同じ分け方です)。

- 識別子は、そのままの語と、camelCase・snake_case・数字の境目で分けた語の
  両方を入れる(`GetBufferPool` → getbufferpool、get、buffer、pool)
- 英語の語尾を少しだけそろえる(複数形の s、-ing、-ed、語末の e)
- 日本語は、2 文字ずつの組にする(「描画処理」→ 描画、画処、処理)
- 質問の側では、英語のよくある語と、ひらがなを含む組を落とす。ひらがなを
  含む組は、助詞や語尾がほとんどで、日本語の文書のどこにでも当たるため
- 本文のほかに、スコープ・シグネチャ・定義している名前の欄と、パスの欄を
  持ち、重みを付ける(既定は、本文 1、名前 4、パス 2)

## 意味検索と、埋め込みモデル

埋め込みは、ONNX の形のモデルを onnxruntime で動かして、手元の CPU で計算
します。PyTorch は使いません。外部の API は呼びません。

### 候補

日本語の質問で英語のコードを探せることが必須なので、多言語のモデルから
選びました。CPU で数万の passage を埋め込める大きさで、配布元に ONNX が
あり、利用の条件が緩いものです。下の表は、配布元(Hugging Face)の情報
です【公式。2026-11-16 に確認】。

| モデル | ライセンス | 大きさ(ONNX) | パラメータ・次元 | 入力の上限 |
| --- | --- | --- | --- | --- |
| `intfloat/multilingual-e5-small`(既定) | MIT | 470 MB | 1.18 億・384 | 512 トークン |
| `ibm-granite/granite-embedding-97m-multilingual-r2` | Apache-2.0 | 390 MB | 0.97 億・384 | 32,768 トークン |

- <https://huggingface.co/intfloat/multilingual-e5-small>
- <https://huggingface.co/ibm-granite/granite-embedding-97m-multilingual-r2>

granite は、モデルカードに、日本語を含む 52 言語と、プログラムのコード
(C・C++ を含む)で学習したと書かれています【公式】。e5-small は、多言語の
汎用のモデルです。どちらも、版(リビジョン)と sha256 を固定して取得
します。

見送ったもの【公式の情報だけで判断。動かしていない】:

| モデル | 見送った理由 |
| --- | --- |
| `intfloat/multilingual-e5-base` | 2.8 億パラメータ(ONNX 1.1 GB)。CPU では数倍遅い見込み |
| `BAAI/bge-m3` | ONNX が 2.3 GB。CPU では、さらに遅い見込み |
| `google/embeddinggemma-300m` | 取得に、利用条件への同意が要る |
| `Alibaba-NLP/gte-multilingual-base`、`Qwen/Qwen3-Embedding-0.6B` | 配布元のリポジトリに ONNX が無い |

大きいモデル 2 つ(`intfloat/multilingual-e5-base` と、
`Alibaba-NLP/gte-multilingual-base` を ONNX にした
`onnx-community/gte-multilingual-base`)は、後から、調整用の質問で近似の
比較をしました(下の「大きい埋め込みモデル」)。

### 手元での比較

公開されている C++ のゲームエンジンの描画まわり(約 1,300 ファイル、
8,623 passage)に、同じ内容の質問を、日本語・英語・その 2 つをつなげた
もの(エージェントが日本語の質問に英語の語を足して検索する形)で、12 件
ずつ投げました。当たりの判定は、「期待する名前を、パス・スコープ・
シグネチャのどれかに含む passage が出たか」という粗いものです【実測】。

上位 5 件に当たりが出た割合(かっこの中は MRR):

| 質問 | 方法 | e5-small | granite |
| --- | --- | --- | --- |
| 日本語 | keyword | 0.00 | 0.00 |
| 日本語 | semantic | 0.25(0.24) | 0.33(0.28) |
| 日本語 | hybrid | 0.25(0.23) | 0.25(0.24) |
| 英語 | keyword | 0.67(0.47) | 0.67(0.47) |
| 英語 | semantic | 0.83(0.72) | 0.50(0.50) |
| 英語 | hybrid | 0.92(0.72) | 0.50(0.52) |
| 日本語 + 英語 | semantic | 0.67(0.58) | 0.58(0.56) |
| 日本語 + 英語 | hybrid | 0.83(0.81) | 0.58(0.51) |

合成のコーパス(`tests/fixtures`。13 ファイル、日本語の文書を含む。答えの
ある質問 15 件)では、逆に、日本語の質問で granite のほうが良い結果
でした(semantic の上位 5 件: granite 87%、e5-small 73%)【実測】。

埋め込みの速さは、どちらも毎秒 45〜55 passage でした。8,623 passage の
索引づくりは、e5-small で 181 秒、granite で 156 秒です【実測】。

同じ 12 件を、約 8 倍の索引(同じエンジンの、描画と基盤のコード。約 8,000
ファイル、72,876 passage)にも投げました。モデルは e5-small です【実測】。

| 質問 | keyword | semantic | hybrid |
| --- | --- | --- | --- |
| 日本語 | 0.08(0.09) | 0.33(0.31) | 0.33(0.31) |
| 英語 | 0.58(0.47) | 0.92(0.70) | 0.75(0.64) |
| 日本語 + 英語 | 0.58(0.47) | 0.83(0.65) | 0.83(0.76) |

- 索引が 8 倍になっても、日本語に英語の語を足した質問の hybrid は、上位
  5 件の割合(0.83)を保った
- 英語だけの質問では、hybrid が semantic を下回った。keyword の順位が
  混ざるためで、どちらが良いかは質問の形による
- 日本語だけの質問は、ここでも弱い(0.33)

### 決めたこと

- 既定は `intfloat/multilingual-e5-small`。実際のコードでは、英語の質問と、
  日本語に英語の語を足した質問で、はっきり良かった。エージェント経由では、
  エージェントが検索の語を作るので、この形になる
- 日本語だけの質問では、どちらのモデルも弱い(上位 5 件で 0.25〜0.33)。
  そのため、skill には、英語のコードを探すときは英語の語を検索に入れる
  よう書いている
- granite は、差し替えの候補として残す。日本語の文書が多いコーパスでは、
  こちらが良いかもしれない
- 質問が 12 件と 15 件の、粗い比較である。実コーパスで、調整用の質問を
  使って、両方を比べるのがよい
- 上の「はっきり良かった」は、名前による粗い判定での話。行の範囲で正解を
  付けて測り直すと、差はもっと小さい(下の「公開の評価例での計測」)

差し替えは、設定で行います。

```toml
[embedding]
model = 'ibm-granite/granite-embedding-97m-multilingual-r2'
```

上の 2 つのほかのモデルを使うときは、ONNX と tokenizer.json を置いた
フォルダを `model_dir` に、取り出し方を `pooling`(`cls` か `mean`)に
書きます。質問と passage の前に付ける文字が要るモデルは、`query_prefix`
と `passage_prefix` に書きます。モデルを変えたら、索引を作り直します
(索引に、作ったときのモデルの名前を残していて、違っていれば keyword に
切り替えて、その旨を知らせます)。

### 中身の無い passage は埋め込まない

ファイルの頭の「ライセンスのコメント + include の並び」や、名前空間の
開き閉じ・前方宣言だけの passage は、埋め込みません(`indexer.py` の
`has_content`)。keyword の索引には入れるので、include の行は keyword で
引けます。

- 埋め込みに渡す文は、頭に場所(パス)を付ける。中身の無い passage は、
  文がほとんどパスだけになる。パスにはクラスの名前が入っているので、
  どの質問にも上位に出て、答えの passage を押し出していた
- 判定するのは、構文で分ける言語(C・C++・C#)だけ。前処理の行(値の
  ある `#define` は除く)、`using`、名前空間の開き閉じ、`extern "C"`、
  前方宣言、括弧だけの行のほかに何も無ければ、中身が無いとみなす。
  コメントは中身として数える(先頭のライセンスのコメントは除く)
- 埋め込まなかった passage のベクトルは 0 で保存し、検索のときに意味検索の
  順位から外す。差分更新では、0 のベクトルを使い回さない
- 前の版で作った索引は、次の `ctxf index` で切り替わる。中身のある passage
  の埋め込みはそのまま使い回すので、埋め込み直しは起きない

O3DE の索引(72,616 passage)では、8,578 件(12%)が中身の無い passage
でした。調整用の日本語の質問 22 件では、直す前は、意味検索の上位 10 件の
37%(hybrid では 13%)をこれが占めていました【実測】。直した前後の当たりの
割合は、下の「公開の評価例での計測」にあります。

ほかのヘッダを include するだけのファイルのように、すべての passage が
中身の無いものになるファイルは、意味検索には出ません(O3DE で 8,069
ファイルのうち 313)。keyword では引けます。埋め込まなかった数は、
`ctxf status` に出ます。

### 速さについて

- 索引づくりの時間は、ほとんどが埋め込みです(上の例で、分割は 3 秒、
  埋め込みは 150〜180 秒)
- スレッドを増やしても、プロセスを分けても、合計の速さはほとんど変わり
  ませんでした(1 プロセスで毎秒 45〜50、3 プロセスで合計 60 ほど)。
  原因は調べきれていません【未確認】。プロセスを分ける設定
  (`[embedding] workers`)はありますが、既定では使いません
- 量子化した ONNX(配布元にあるもの)も、この PC では速くなりません
  でした【実測】
- GPU では、7 倍ほど速くなります(下の「GPU で計算する」)

### GPU で計算する

索引づくりの埋め込みは、入っている onnxruntime に GPU の実行先があれば、
GPU で計算します(設定の `[embedding] device`。既定は `auto`)。検索の
ときの質問の埋め込みは、いつも CPU です。短い文 1 つなので速さは変わらず、
GPU のセッションは作るのに時間がかかるためです。

Godot の全体(69,406 passage。うち 68,593 を埋め込む)で、索引を最初から
作って比べました【実測】。GPU は GeForce RTX 5070 Ti、実行先は DirectML
(onnxruntime-directml 1.24.4)です。

| 計算先 | 索引づくり | うち埋め込み | 埋め込みの速さ |
| --- | ---: | ---: | ---: |
| CPU(16 コア。ほかの作業と並行) | 4,959 秒 | 記録なし | 毎秒 14 ほど |
| GPU | 290 秒 | 240 秒 | 毎秒 286 |

- CPU だけで単独に動かしたときの速さは、毎秒 45〜50 passage(上の
  「速さについて」)。GPU は、その 6〜7 倍
- GPU で作った索引と、CPU で作った索引は、passage が同じで、ベクトルも
  一致した。埋め込んだ 68,593 件のコサイン類似度は、最小でも 1.00000
  (16 ビットで保存した値どうし)。検索だけの評価の数字(上位 1・5・10 件、
  MRR、根拠の再現率)も、3 つの手法ですべて同じだった
- そのため、差分更新は、計算先が違っても、前の索引の埋め込みを使い回す
- 束の大きさは、GPU では 32 以上にする(同じ 4,000 件で、16 なら毎秒 263、
  32 なら 320、64 なら 338、128 なら 341)。CPU の既定は 8
- 実行先は、DirectML(Windows の DirectX 12 の GPU。メーカーを問わない
  【公式】)と CUDA(NVIDIA)の名前を見て選ぶ。動かして確かめたのは
  DirectML だけで、CUDA は確かめていない【未確認】
- 配布元は、DirectML を、新しい機能を足さない段階(sustained engineering)
  としている【公式】。メモリの使い回しの最適化と並列の実行には対応して
  いないので、その 2 つを切ってセッションを作る【公式】
  <https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html>
- GPU の実行先があっても始められないとき(ドライバーが古いなど)は、
  `auto` なら、そう知らせて CPU で続ける。`device = "gpu"` なら止まる。
  `device = "cpu"` で、GPU を使わない

入れ方: GPU 用の onnxruntime は、CPU 用と同じ名前のモジュールを入れるので、
両方は入れられません。入れ替えます。

- プラグインとして入れた人: `python -I "<プラグインのフォルダ>\ctxf.py"
  setup --gpu`。選び方は覚えていて、依存が変わって `setup` をやり直す
  ときにも引き継ぐ。`setup --cpu` で戻す
- リポジトリを取得した人: 取得したフォルダで `.venv\Scripts\python -m pip
  uninstall -y onnxruntime` のあとに、`.venv\Scripts\python -m pip install
  onnxruntime-directml`。`setup.bat` をもう一度実行すると、CPU 用が上から
  入るので、そのときはやり直す

## hybrid

keyword と semantic の順位を、RRF(Reciprocal Rank Fusion。順位の逆数の和)
でまとめます。それぞれ上位 50 件を取り、定数は 60 です。

keyword の側には、重みを掛けます。重みは、質問の語のうち、索引に 1 回
でも出てくる語の割合の平方根です(`[search] hybrid_weighting = 'equal'`
で、重みなしにできます)。日本語の質問で英語のコードを探すときは、keyword
に当たる語がほとんど無く、たまたま当たった 1 語の結果が上位を占めるため
です。

用語の対応表で質問に語を足したときは、足した語と、元の質問の英字の語で
割合を見ます(下の「日本語の質問」)。日本語の質問の 2 文字の組は、英語の
コードにはほとんど無いので、それも数えると、足した語が効かないためです。

reranker は、後段に差し込めます(Python から `Searcher(..., reranker=関数)` で
渡したときだけ。評価やテストのため)。既定では使いません。設定ファイルの
`[search] reranker` は 0.4.0 で外しました。作業フォルダの `.cf/config.toml` は、
取ってきたリポジトリに入っていることもあり、そこから Python のコードを
読み込ませると、読み取り専用のはずの検索が、任意のコードを動かせてしまうためです。

## 日本語の質問

日本語だけの質問で英語のコードを探すと、keyword には語がほとんど当たらず、
意味検索も弱くなります。日本語に英語の語を足すと、どちらも大きく良くなります
(下の表の「日本語+英語」)。そこで、検索の前に、用語の対応表で質問に英語の
語を足します(`glossary.py`)。

- 既定の対応表(`glossary_ja.tsv`)は、ゲームエンジンとプログラミングの
  一般の語だけ(約 210 語)。「処理」「仕組み」「関数」のように、どのコードに
  も当たる語は入れない。入れると keyword の重みが上がるだけで、順位が乱れた
- 作業フォルダの対応表(`.cf/glossary.tsv`)を先に当てる。エンジンに固有の
  語や、別のエンジンの用語との対応を、チームで書く
- 質問の英字の語が 3 つ以上あるとき(エージェントがすでに英語の語を足した
  とき)は、既定の対応表を当てない。当てると、下の表の「日本語+英語」の
  順位がかえって下がった
- 足した語は、結果の note(`added terms from the glossary: …`)と JSON の
  `added_terms` で知らせる。評価の記録(`runs.jsonl`)には、対応表を使ったか
  と、作業フォルダの対応表のハッシュを残す
- カタカナだけの語は、前後がカタカナでないときだけ当てる(「ロック」を
  「ブロック」に、「ログ」を「ダイアログ」に当てない)。照合の前に、質問と
  語を NFKC でそろえる(半角カナ・全角英数)
- 英語の語は、空白で区切られた、小文字を含む英字の語だけを数える(GPU の
  ような略語や、`std::vector`・`src/render/buffer.cpp` のような名前とパスは
  数えない)
- 対応表の書き方の誤った行は飛ばし、結果の note で場所を知らせる

公開されている C++ のゲームエンジン(O3DE)の索引(約 7 万 passage、モデルは
e5-small)で測りました【実測】。正解は、パス・スコープ・シグネチャに期待する
名前を含む passage という粗い判定です。上位 5 件に正解がある割合
(hit@5)と、上位 10 件の割合(hit@10)です。

| 質問 | 手法 | 対応表なし hit@5 / hit@10 | 対応表あり hit@5 / hit@10 |
| --- | --- | ---: | ---: |
| 描画まわりの 12 問、日本語だけ | keyword | 0.08 / 0.08 | 0.83 / 0.83 |
| 同上 | semantic | 0.33 / 0.33 | 0.67 / 0.75 |
| 同上 | hybrid | 0.33 / 0.33 | 0.67 / 0.83 |
| 同上、日本語+英語 | hybrid | 0.83 / 0.92 | 0.83 / 0.92 |
| 基盤まわりの 10 問、日本語だけ | keyword | 0.10 / 0.10 | 0.50 / 0.50 |
| 同上 | hybrid | 0.70 / 0.80 | 0.80 / 0.90 |
| 合成のコーパスの日本語の 9 問 | hybrid | 0.56 / 0.89 | 0.78 / 1.00 |

- 基盤まわりの 10 問は、対応表を書いた後に作った(対応表に合わせていない)
  問題。ただし、一般の語を外すかどうかは、描画まわりの 12 問と合成の
  コーパスの結果を見て決めたので、その分の偏りはある
- 日本語だけの質問は、対応表があっても、エージェントが英語の語を足した質問
  (0.83)には届かない。そのため、skill は英語の語を足して検索するよう書き、
  対応表は、エージェントが英語にしなかったときと、別のエンジンの用語の対応
  に使う
- 質問の数が少ないので、差は目安。実コーパスで比べて決める
- この節と「手元での比較」の数字は、名前による粗い判定で、甘く出ている。
  行の範囲で正解を付けて測り直した数字は、次の「公開の評価例での計測」

## 公開の評価例での計測

ここまでの表は、期待する名前がパス・スコープ・シグネチャに入っていれば
当たりと数える、粗い判定でした。行の範囲で正解を付けた評価例
([examples/o3de](../examples/o3de/README.md)。評価用 27 問、調整用 22 問)
を作り、測り直しました【実測】。題材は同じ O3DE のコード、モデルは
e5-small です。索引は 0.2 で作り直したもので、72,616 passage です(上の
表と「規模と時間」の 72,876 passage は、0.1 で作ったときの数)。数字は、
上位 5 件に正解の passage がある質問の割合で、かっこの中は上位 10 件です。

調整用の 22 問は、上の表の「描画まわりの 12 問」と「基盤まわりの 10 問」と
同じ質問です。粗い判定では hybrid の上位 5 件が 0.67 と 0.80 でしたが、
行の範囲の正解では、どちらも 0.50 でした。

### 中身の無い passage を埋め込まない前後

| 質問 | 手法 | 前 | 後 |
| --- | --- | ---: | ---: |
| 調整用(日本語だけの 22 問) | keyword | 0.41(0.45) | 0.41(0.45) |
| 同上 | semantic | 0.27(0.41) | 0.41(0.59) |
| 同上 | hybrid | 0.50(0.64) | 0.55(0.68) |
| 評価用(答えのある 24 問) | keyword | 0.50(0.58) | 0.50(0.58) |
| 同上 | semantic | 0.50(0.54) | 0.54(0.54) |
| 同上 | hybrid | 0.50(0.58) | 0.54(0.58) |

上位 5 件・10 件から外れた質問はありませんでした(調整用の hybrid で、

評価用の hybrid(後)の内訳は、文書がからむ質問(`doc_to_code`・
`code_to_doc`)が 6 問すべて、名前の分かっている質問が 4 問中 3 問、似た
実装を探す質問が 5 問中 2 問、名前を知らずに言葉で聞く質問が 9 問中 2 問
です。しきい値(上位 5 件に 80%)には届いていません。

### 用語の対応表の有無

調整用の日本語だけの 22 問、直した後の索引です。

| 手法 | 対応表なし | 対応表あり |
| --- | ---: | ---: |
| keyword | 0.00(0.00) | 0.41(0.45) |
| semantic | 0.14(0.23) | 0.41(0.59) |
| hybrid | 0.09(0.23) | 0.55(0.68) |

対応表は、この質問の結果を見て決めたものなので、差は大きめに出ています。

### 質問を英語にしたとき

同じ 22 問を、英語の文に直したものと、日本語の後ろに英語の文をつなげた
もので測りました(直した後の索引)。

| 質問 | keyword | semantic | hybrid |
| --- | ---: | ---: | ---: |
| 日本語(対応表あり) | 0.41(0.45) | 0.41(0.59) | 0.55(0.68) |
| 英語の文 | 0.23(0.32) | 0.55(0.59) | 0.36(0.50) |
| 日本語 + 英語の文 | 0.23(0.32) | 0.50(0.55) | 0.45(0.59) |

- hybrid では、英語の文は、対応表で語を足した日本語を下回った。ただし、
  対応表はこの 22 問の結果を見て決めたものなので、日本語の側に有利な比較に
  なっている。semantic だけなら、英語の文のほうが良い(0.55 と 0.41)。
  対応表を合わせていない評価用の質問では、hybrid の上位 5 件は、英語の
  質問(8 問)が 75%、日本語の質問(16 問)が 44% だった
- 粗い判定では「日本語 + 英語」が最も良く見えていた(0.83)が、行の範囲の
  正解では、そこまでの差は出ない
- 英語の文では keyword が弱い(文の中の一般の語が、関係の無い passage に
  当たる)。そのため、hybrid が semantic を下回る
- エージェントは、文ではなく語を並べて検索することが多く、skill もそう
  書いている。その形での当たりの割合は、エージェントを使う手法
  (`agent_cf`)で測る必要がある【未確認】

### reranker(採らなかった)

hybrid の上位 30 件を cross-encoder で並べ直す形を、調整用の日本語だけの
22 問で試しました。候補は、配布元(Hugging Face)に ONNX があり、利用の
条件が緩いものです【公式。2026-11-16 に確認】。表は、reranker の順位と
元の順位を RRF でまとめたときの数字です。

| reranker | ライセンス | 大きさ | 上位 5 件(10 件) | 1 回の時間 |
| --- | --- | ---: | ---: | ---: |
| なし | | | 0.55(0.68) | |
| `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | Apache-2.0 | 471 MB | 0.50(0.68) | 0.6 秒 |
| 同上の、8 ビットに量子化したもの | Apache-2.0 | 119 MB | 0.45(0.68) | 0.5 秒 |
| `onnx-community/gte-multilingual-reranker-base`(8 ビット) | Apache-2.0(元のモデル) | 341 MB | 0.59(0.68) | 1.4 秒 |
| `hotchpotch/japanese-reranker-xsmall-v2` | MIT | 147 MB | 0.59(0.77) | 0.3 秒 |

- 最も良いものでも、上位 5 件は 22 問中 1 問増えるだけで、しきい値には
  届かない
- 上位 30 件の候補に正解が入っている質問は 82%。並べ直しでは、これより
  上には行けない
- 英語の文の質問では、hybrid の 0.36 が、gte で 0.64、日本語のモデルで
  0.55 になった。英語の文で聞く使い方が多いなら、効く見込みがある
- 時間は、上位 30 件を並べ直す 1 回の中央値で、ほかの重い処理が無い
  ときに 12 問で測ったもの。検索の時間に、これが足される。索引づくりなどと
  CPU を取り合うと、3〜7 倍に延びた
- 既定には入れない。モデルの取得と検索の時間が増えるわりに、日本語の
  質問での差が小さい。差し込み口(`Searcher` の引数 `reranker`)は残してあるので、
  実コーパスで試せる
- 見送ったもの: `BAAI/bge-reranker-v2-m3`(2.3 GB。配布元に ONNX が無い)、
  `jinaai/jina-reranker-v2-base-multilingual`(非商用のライセンス)

### 大きい埋め込みモデル(採らなかった)

既定の e5-small(1.2 億パラメータ)より大きいモデルを 2 つ、調整用の
22 問で試しました。索引全体を埋め込み直す代わりに、質問ごとの候補(今の
モデルの意味検索の上位 300 件、keyword の上位 50 件、正解の passage。
合わせて 9,918 passage)だけを埋め込んで、並べ直しています。今のモデルの
上位 300 件に入らない passage とは比べていないので、大きいモデルに少し
有利に出る、近似の数字です【実測】。

| モデル | 大きさ | 日本語 semantic | 日本語 hybrid | 英語の文 semantic | 英語の文 hybrid |
| --- | ---: | ---: | ---: | ---: | ---: |
| `intfloat/multilingual-e5-small`(既定) | 470 MB | 0.41(0.59) | 0.55(0.68) | 0.55(0.59) | 0.36(0.50) |
| `intfloat/multilingual-e5-base` | 1.1 GB | 0.55(0.77) | 0.45(0.64) | 0.59(0.68) | 0.41(0.55) |
| `onnx-community/gte-multilingual-base` | 1.3 GB | 0.50(0.77) | 0.55(0.68) | 0.50(0.68) | 0.50(0.68) |

ライセンスは、e5-base が MIT、gte が Apache-2.0(元のモデル)です【公式】。

- semantic の上位 10 件は、どちらも良くなった(日本語で 0.59 → 0.77)。
  上位 5 件と hybrid では、良し悪しが混ざる
- e5-base は、日本語の質問で正解が 1 位に来る数が減り(6 問 → 1 問)、
  hybrid が下がった
- gte は、英語の文の質問で hybrid が 0.36 → 0.50 になった。日本語の質問の
  hybrid は変わらない
- 埋め込みは、どちらも毎秒 6〜7 passage だった。ほかの重い処理と並行で
  測った値で、既定のモデルの単独での値(毎秒 40〜55)とは、そのまま
  比べられない。層の数が同じで幅が 2 倍なので、計算は 4 倍ほど重い
  見込み【未確認】
- 既定は変えない。モデルの取得が 2〜3 倍、索引づくりが数倍になるのに、
  日本語の質問の hybrid が良くならない。試すときは、設定で差し替えられる
  (上の「決めたこと」)
- 索引全体を埋め込み直しての計測は、していない【未確認】

## 保存

外部のサービスを使わない、SQLite の 1 ファイルです。

| 表 | 中身 |
| --- | --- |
| `files` | 索引に入れたファイル(大きさ・更新日時・行数) |
| `chunks` | passage(場所・種類・スコープ・シグネチャ・本文。本文は縮めて持つ) |
| `chunks_fts` | keyword の索引(FTS5。本文は持たない) |
| `vectors` | 埋め込み。passage の順に並べ、4,096 件ごとに 1 行で持つ |
| `meta` | 形式の版、作成日時、統計、かかった時間、埋め込みモデル。0.4.0 からは、作るたびに変わる `build_id` と、質問の前置き(`query_prefix`)も。どちらも無くてよい(0.3.1 の索引はそのまま読める) |

- 埋め込みは、16 ビットの浮動小数で保存する(32 ビットの半分の大きさ)。
  検索のときに 32 ビットに直して、全部の passage との内積を取る(総当たり)
- 途中のファイル(`index.db.tmp-<番号>`)に書いて、できあがってから
  置き換える(下の「差分更新」)
- ベクトル DB は使っていない。245,457 passage まで、総当たりで足りた
  (下の「規模と時間」)。それを超える規模は、測っていない
- 検索は、検索のたびに索引を開き直す。MCP サーバーが読み込んだベクトルは、
  索引の `build_id`(0.3.1 の索引では meta 全体)で、今の索引と同じかを
  確かめ、違えば読み直して検索し直す(作り直しの最中の検索が、古い番号で
  新しい索引の passage を返さないため)
- 埋め込みの設定(pooling・前置き・ONNX のファイル・入力の長さなど)が、
  索引を作ったときと違うときは、意味検索をやめて keyword にし、note で
  知らせる(違う設定のベクトルどうしを比べないため)

## 差分更新

索引づくりのほとんどは埋め込みの時間です。埋め込みは、変わった passage の
分だけを計算し、ほかは前の索引から使い回します。0.4.5 からは、分割も、
中身の変わらないファイルの分は分け直さずに、前の索引の passage を写します
(下の「分割を写す」)。

### 埋め込みを使い回す

- 使い回すかどうかは、埋め込みに渡す文そのもの(場所・スコープ・
  シグネチャ・本文)のハッシュで決める。変更の検知に版管理(git など)は
  使わない。ファイルの先頭に行を足して後ろの passage の行番号がずれても、
  文が同じなら使い回す
- 埋め込みの作り方(モデル・版・次元・ONNX のファイルと大きさ・pooling・
  入力の長さ・passage の前置き・保存の形・文の作り方の版)が前の索引と
  違えば、すべて埋め込み直す
- 消えたファイルの passage は、新しい索引に入らない
- `ctxf index --full` で、使い回さずに作り直せる(下の `index.db.partial`
  も使わずに消す)
- 形式の版が違う前の索引からも、表を読めて、埋め込みの作り方が同じなら、
  使い回す(使い回す鍵は、モデルに渡す文そのもののハッシュなので)
- 計算した埋め込みは、1,024 passage ごとと、止められたときに
  `index.db.partial` に書く。次の索引づくりは、埋め込みの作り方がまったく
  同じときだけ、それを使い回して続きから計算する(`--full` では使わない)。
  鍵と長さの合わない行は使わず、ファイルを読めなければ消して続ける。
  埋め込みつきの索引ができあがったら消す。`--no-embed` で作ったとき(と、
  モデルを読めずに keyword だけで作ったとき)は残して、次に埋め込みつきで
  作るときに使う。設定で埋め込みを切った(`[embedding] enabled = false`)
  索引ができあがったときは、使われないので消す
- `.cf` の中の、`index.db.partial` と作っている途中の索引の名前にリンクが
  あれば、たどらずにリンクだけを消してから書く。`.cf/.gitignore` は、その
  名前で何かがあれば書かない
- 置き換えられなかったとき(Windows で、ほかのプログラムが索引を開いて
  いる)は、40 回(約 10 秒)繰り返したあと、できあがった索引を
  `index.db.new` に残して止まる。次の索引づくりは、そこから使い回す。
  検索の側は `.new` に切り替えない(MCP サーバーは読み取り専用のまま)
- 止められたときの途中のファイル(`index.db.tmp-<番号>`)は、その番号の
  プロセスがもう無ければ、次の索引づくりが消す。番号が ASCII の数字で
  10 桁までのものだけを見て、ほかの名前のファイルには触れない
- 前の索引に埋め込みがあるのに、モデルを読めないときは、keyword だけの
  索引に置き換えずに止まる(`--no-embed` を付ければ置き換える)。取り込み
  より前に確かめるので、止まるまでに時間はかからない
- source のルートが無いときは、何も書かずに止まる(ドライブが外れていた
  日に、その source の分が索引から消えないため)

O3DE の一部(121 ファイル、約 950 passage)で測りました【実測】。

| 場面 | 埋め込んだ passage | 使い回した passage | 時間 |
| --- | ---: | ---: | ---: |
| 最初の索引 | 951 | 0 | 20.4 秒 |
| 何も変えずにもう一度 | 0 | 951 | 1.2 秒 |
| 3 ファイルを変え・1 つ消し・1 つ足した | 4 | 944 | 1.3 秒 |
| 同じコーパスを作り直し(`--full`) | 948 | 0 | 19.2 秒 |

さらに 5 ファイルを変えて差分更新したものと、同じコーパスを作り直した
ものを比べ、passage と埋め込みが 948 件すべて一致し、検索の上位 10 件の
順位も一致しました【実測】。埋め込みの計算は、まとめて計算する相手によって
浮動小数の末尾が変わりうるので、厳密な一致を保証するものではありません。
16 ビットに丸めて保存するので、この計測では差が出ませんでした。

### 分割を写す

0.4.4 までは、変わったファイルが無くても、毎回すべてのファイルを分け
直していました(Godot の 4,996 ファイルで、差分更新の 60.4 秒のうち 57.7 秒が
取り込みと分割)。0.4.5 からは、中身の変わらないファイルは、前の索引の
passage をそのまま写します。

- ファイルは、今までどおりすべて読む(読むのは取り込みの時間の 4% ほど)。
  写すのは、source・パス・言語・本文(文字コードを直し、改行をそろえた
  後のもの)のハッシュが、前の索引と同じファイルだけ。大きさと更新日時
  では見分けない(同じ大きさ・同じ更新日時のまま中身が変わっても、取り
  こぼさない)
- 分割の作り方が前の索引と 1 つでも違えば、すべて分け直す。比べるのは、
  `[chunk]` の設定のすべて、分け方のコード(`chunking` の .py の中身の
  ハッシュ。版を上げずにコードを変えたときも分け直す)、構文の解析器
  (tree-sitter と、C・C++・C# の文法)の版、道具の版、索引の形式の版
- 構文で分けられずに行で分けたファイルは写さない(分け直して、作り直した
  ときと同じ注意を出す)
- ファイルを書く順は今までと同じなので、passage の番号(同点の順位を
  決める)も、作り直したときと同じになる
- keyword の索引は本文を持たない形(FTS5 の contentless)なので、写した
  passage も語を分け直して入れる。識別子を分けた結果は覚えて使い回す
  (出す語は同じ。下の計測で 2.4 倍)
- 分割の控えは、表 `file_chunking`(ファイルごとの本文のハッシュと分割の
  統計)と meta の `chunking` に持つ。検索では使わない。0.4.4 までの索引
  には無いので、0.4.5 の最初の索引づくりは、すべて分け直す
- `--full` では写さない(すべて分け直し、すべて埋め込み直す)

手元の Linux の機械(4 コア)で、C++ の標準ライブラリと Linux のヘッダー
(1,313 ファイル、14,195 passage)を、埋め込みなしで測りました【実測】。

| 場面 | 取り込みと分割 |
| --- | ---: |
| 0.4.4(すべて分け直す) | 10.2 秒 |
| 0.4.5、最初の索引(識別子の分け方を覚えるだけ) | 7.1 秒 |
| 0.4.5、何も変えずにもう一度 | 3.7 秒 |
| 0.4.5、3 ファイルを変え・1 つ足し・2 つ消し・1 つの更新日時を変えた | 4.0 秒 |

最後の場面の索引を、同じコーパスを作り直した索引と比べ、ファイル・
passage(14,147 件)・keyword の索引の語(91,766 語)と出た位置・meta(作った
日時と時間を除く)がすべて一致しました【実測】。埋め込みつきでの一致は、
テスト(`tests/test_chunk_reuse.py`)で、テスト用の埋め込みで確かめて
います。Windows と、大きいコーパスでの時間は、まだ測っていません
【未確認】。

## 規模と時間

公開されている C++ のゲームエンジンの一部で測りました【実測】。16 コアの
CPU で、GPU は使っていません。モデルは e5-small です。大きいほうの
索引づくりは、ほかの作業と並行だったので、単独ならもう少し速いはずです。

| 項目 | 小さい索引 | 大きい索引 |
| --- | ---: | ---: |
| ファイル | 1,345 | 8,069 |
| 行 | 16 万 | 143 万 |
| ソースの大きさ | 6.7 MB | 59.4 MB |
| passage | 8,623 | 72,876 |
| 索引づくり | 181 秒 | 1,888 秒 |
| うち、取り込みと分割 | 3 秒 | 36 秒 |
| うち、埋め込み | 178 秒 | 1,852 秒 |
| 索引の大きさ | 18.2 MB | 134.8 MB |
| 索引づくりのメモリの最大 | 1.37 GB | 1.39 GB |

検索 1 回の時間です。「起動したまま」は、MCP サーバーの形(索引とモデルを
読み込んだ後)、「毎回起動」は、skill の形(コマンドを 1 回ずつ起動し、
出力が出るまで)です。

| 項目 | 小さい索引 | 大きい索引 |
| --- | ---: | ---: |
| 起動したまま keyword(p50 / p95) | 1.6 / 3.1 ms | 3.8 / 10.8 ms |
| 起動したまま semantic(p50 / p95) | 8.8 / 32.7 ms | 8.9 / 10.5 ms |
| 起動したまま hybrid(p50 / p95) | 10.4 / 21.8 ms | 13.9 / 27.8 ms |
| 起動したままの最初の 1 回(読み込み) | 約 1.0 秒 | 約 1.8 秒 |
| 毎回起動 keyword(中央値) | 0.29 秒 | 0.25 秒 |
| 毎回起動 hybrid(中央値) | 1.6 秒 | 2.0 秒 |

- 最初の索引づくりの時間は、passage の数にほぼ比例する(毎秒 40〜50
  passage)。2 回目からは、変わった passage の分だけ(上の「差分更新」)
- もっと大きい索引でも測った【実測】。公開されていない C++ のエンジンの
  コードの一部で、19,030 ファイル、624 万行、245,457 passage。索引づくりは
  GPU で 1,170 秒(分割 185 秒、埋め込み 980 秒)、索引は 488.9 MB(passage
  の数に比例)。起動したままの検索は、hybrid が中央値 99.5 ミリ秒、p95
  228.3 ミリ秒(keyword が 107.3 と 286.2、semantic が 59.8 と 116.1)。
  約 7 万 passage のときより遅くなるのは、主に keyword(BM25)のほう。
  モデルとベクトルの読み込みは 3.7 秒、持ち続けるメモリは 1.2 GB ほど。
  質問は、別のコードのための 85 問の文をそのまま使ったので、ここで見て
  いるのは速さだけ
- 索引の大きさは、ソースの 2.3〜2.7 倍
- 約 7 万 passage では、総当たりの意味検索は 10 ミリ秒ほどで、ほとんどが
  質問の埋め込みの時間。検索時間のしきい値(3 秒)には、どちらの形でも
  収まる
- 毎回起動の形の時間は、ほとんどが、Python の起動と埋め込みモデルの
  読み込み

## 出力

- エージェント向けの形は、英語の短い文面。1 件ごとに、場所
  (`source:path:行-行`)、種類、スコープ、シグネチャ、本文を返す
- 上位の passage は本文ごと、収まらない分は場所だけを返して、全体を
  12,000 バイトに収める(`[search] max_output_bytes`。上限は 18,000)。
  Copilot CLI は、20 KiB を超える道具の結果をモデルに渡さず、ファイルに
  退かせる【公式】
- 上限を守る。0.3.1 の見積もり(場所だけの行を 1 行 150 バイト)で
  収まる出力は、0.3.1 と同じ。収まらないときは、場所だけの行のシグネチャを
  後ろから落とし、それでも収まらなければ実際の大きさで並べ直し、最後は
  `(+N more matches, not shown)` にまとめる。並べ直しでは、消えたファイルの
  場所の行の分を、ほかの場所の行より先に取っておく。それでも超えるときは、
  決まって出す部分を正確に数えて、もう一度並べる。場所の行だけで上限を
  超えるとき(上限を小さくしたときなど)は、消えたファイルの行も後ろから
  落として `(+N more matches, not shown)` に数える(頭の `stale:` の行は
  残る)。とても長い 1 行(400 バイト以上)で本文が止まり、1,000 バイト
  以上が余ったときは、後ろの passage にも本文を出す
- 上限を超えるのは、決まって出す部分(頭の行、note、古い passage の 1 行と
  終わりの段落、`roots:` の行)に、`More matches` の見出しと件数の行
  (合わせて 60 バイトほど)を足した大きさが上限を超えるときだけ。上限を
  最小の 1,000 バイト近くにして、古い passage と長いルートがあるときに
  起きうる
- 上限は、改行を LF として数えたバイト数。Windows で CLI の出力をパイプや
  ファイルに受けると、改行が CRLF になり、行の数だけ増える(MCP では
  増えない。既定の 12,000 では、ふつうのコードなら、行の数を足しても
  20 KiB に届かない。上限を
  18,000 近くに上げて、とても短い行の本文が並ぶと、超えることがある)
- 索引の後に変わったファイルを指す結果には `[changed since index]`、
  消えたファイルには `[file no longer exists]`(本文は出さない。人が読む
  形は「※索引の後に消えたファイル」の印と索引のときの本文、JSON は本文と
  `missing: true`)の印を
  付け、頭に件数の 1 行と、終わりに引用の前に確かめるよう求める段落を
  足す。印が無ければ、どちらも出ない
- source のルートが作業フォルダそのものでないときは、`roots:` の 1 行で
  ルートを出す(エージェントが `source:path` を開けるように)。作業フォルダ
  の中のルートは作業フォルダからの相対パス、外のルートは設定の絶対パスで
  出る(検索のたびにモデルに送られる)
- 質問の語は、異なる語の最初の 256 個までを使う(keyword の側)。とても
  長い質問で SQLite の変数の上限を超えたり、何分も止まったりしないため。
  256 個までの質問では、順位は変わらない。超えたときは、その旨の note を
  出す。用語の対応表で足した語は、質問の後ろの語より先に残す

## MCP サーバー

- 標準ライブラリだけで、stdio の JSON-RPC を扱う
- ツールは `search`(`query`・`top_k`・`mode`・`source_id`)と `status`
  だけ。書き込みと、索引に無いファイルの読み出しはしない
- 標準出力には JSON-RPC の行だけを書く。形の崩れた要求には JSON-RPC の
  誤りで答え、思わぬ例外も `Internal error` で答えて、サーバーは落ちない
  (詳しいことは標準誤差に書く)。`NaN`・`Infinity` を含む要求は Parse
  error、`id` が有限の数でない要求は Invalid Request(どちらも `id` は
  null)。答えを JSON にできないときは、決まった `Internal error` の 1 行を
  書く
- 設定を読めないとき(UTF-8 でない、TOML の誤り、項目の形の誤り)も、
  起動の挨拶には、索引のある作業フォルダの指示で答え、理由は道具を
  呼んだときの誤りの文で返す
- 8,192 バイトを超える質問は断る
- `.cf` か索引の無い作業フォルダでは、起動の挨拶の指示を「grep で探す」
  の 1 文にする。索引のある作業フォルダの指示は、計測した形のまま
- 索引の無い作業フォルダでは、道具の一覧を空で返す(定義は使わない回でも
  毎回モデルに送られ、2 つで 381 トークンになる)。挨拶では
  `listChanged: true` と答え、裏のスレッドが 3 秒おきに索引の有無を見て、
  変わったら `notifications/tools/list_changed` を送る。見るのは、設定の
  ファイルを親へ探すことと、索引のファイルがあるかだけ。返事と知らせが同じ
  行に混ざらないよう、標準出力への書き込みは鍵で 1 つずつにする。Copilot
  CLI 1.0.114 は、知らせの後、次にモデルを呼ぶときに一覧を取り直した【実測】
- 起動したままなので、埋め込みモデルとベクトルを読み込んだまま保てる
- 索引のある作業フォルダでは、起動の挨拶(initialize)のときに、裏の
  スレッドで埋め込みモデルとベクトルを読み込み始める。エージェントの
  モデルが最初の応答を返すまでの間に済むので、最初の検索も待たせない
  (Godot の約 7 万 passage で、読み込みを待つと 1.2 秒、済んでいれば
  0.03 秒【実測】)。持ち続けるメモリは 0.9 GB ほど。`[search] preload =
  false` で止められる
- 設定(`.cf`)は、エージェントの作業フォルダから親へ探す。エージェントの
  作業フォルダは、ホストが環境変数(Copilot CLI の `COPILOT_SESSION_CWD`)で
  知らせていればその場所、無ければサーバーの作業フォルダ。プラグインの
  MCP サーバーは、プラグインのフォルダを作業フォルダにして起動される
  ため【実測】
- ツールの定義は、使わない回でも毎回モデルに送られるので、短くしている
- ツールの説明と、プラグインの hook が足す始めの 1 文は、「探すときは、
  検索を grep より先に」と書く。「名前を知っているなら grep」と書いて
  いた 0.2 では、モデルが覚えている識別子で grep から始め、検索を使わ
  なかった([copilot.md](copilot.md) の「出し方」)
- 入口の `ctxf.py` は、最初の用意が済んでいない PC で MCP サーバーとして
  起動されたとき、道具を 1 つも出さないサーバーとして答え続ける(誤りの
  文を標準出力に書いて終わると、ホストには壊れたサーバーに見える)。この
  サーバーも、標準出力には JSON の行だけを書く。形の崩れた行(`NaN`・
  `Infinity` を含むもの、深すぎる JSON も)は読み飛ばし、答えを JSON に
  できない要求(`id` が `1e999` など)には答えない

## プラグインと、Python の置き場

Copilot のプラグインとして入れたとき、プラグインのフォルダは更新のたびに
置き換わります。そのため、Python の依存(約 200 MB)は、プラグインの外の
利用者ごとの置き場に置きます(`ctxf.py`)。

- 入口の `ctxf.py` は標準ライブラリだけで動き、使える python を探して、
  プラグインの `src` のパッケージを動かす。探す順は、環境変数 `CF_PYTHON`、
  隣の `.venv`(リポジトリを取得して `setup.bat` を使う人)、利用者ごとの
  置き場の仮想環境(`ctxf.py setup` が作る)
- 利用者ごとの置き場の仮想環境は、作ったときの依存の一覧のハッシュを
  覚えておく。プラグインを更新して一覧が変わったら、動かさずに「もう一度
  setup を」と知らせる。一覧が同じなら、更新してもそのまま動く
- `setup` は、壊れた仮想環境を作り直し、依存を読み込めることを確かめてから
  覚え書きを書く。同時に 2 つ走らないよう排他する。pip が 0 で終わったのに
  依存を読み込めないとき(仮想環境の Python が同じフォルダのまま別の版に
  置き換わった、パッケージの一部が壊れたなど。pip は入れたものの記録だけを
  見るので、入れ直さない)は、読めない理由を出して、仮想環境を
  `venv --clear` で 1 回だけ作り直して入れ直す。それでも読めなければ、
  仮想環境のフォルダを消すよう知らせて 1 で終わる。`setup.bat` も、入れた
  後に依存を読み込めるかを確かめ、同じように `.venv` を 1 回だけ作り直す
- hook は仮想環境の python を起動しない(セッションの始まりを遅くしない)。
  何があっても 0 で終わり、セッションを止めない
- hook は、索引の古さを `index.db` の更新日時だけで見る(作り直しはファイル
  を置き換えるので、作った時刻になる)。索引は開かない(Windows で、作り
  直しの置き換えを妨げないため)。7 日(`CF_INDEX_AGE_WARN_DAYS`)以上たって
  いれば、いつもの文の後に 1 文を足す(0.4.13 から)
- 仮想環境のもとの Python が消えていたら(`pyvenv.cfg` の `home` が無い)、
  起動する前に「set up with a Python that is no longer installed」と
  知らせる。Windows 以外では、`bin/python` の指す先の名前が
  `python<版>` で、その版が `pyvenv.cfg` の版と違うときも同じに扱う。
  Windows で、仮想環境の起動が終了コード 103(もとの Python が見つから
  ない)で終わったときも、同じに扱う
- 隣の `.venv` が壊れているときは、利用者ごとの置き場に切り替えない。
  直すコマンドとして、`setup.bat` を示す(Windows 以外では、`.venv` を
  `python3 -m venv --clear` で作り直して `pip install -e .` する 1 行)。
  `ctxf.py setup` は利用者ごとの置き場に作るだけで、隣の `.venv` が先に
  選ばれ続けるため
- 子(`ctxf.py --run`)が、要るパッケージを読めないとき(仮想環境の
  python が別の版に替わったなど)は、標準入力を読む前に終了コード 104 で
  終わる。入口は、それを用意ができていないときと同じに扱う(`serve` は
  道具を出さないサーバー、ほかは終了コード 4)。`CF_PYTHON` で python を
  選んだときは、104 をそのまま返す。道具そのもの(`context_foundation` の
  モジュール)の import の誤りは、依存を読めないのではないので 104 に
  しない(traceback を出して 1 で終わる)。`where` は仮想環境の python を
  見つけたことだけを `python:` の行に出すので、このときの手がかりは
  `model: unknown (ImportError: …)` などの行になる
- 入口は、子が終わるのを待つ間に Ctrl+C を受けても、子を止めずに子の
  後始末(途中までの埋め込みを書き残すなど)を待ち、子の終了コード(130)を
  返す。Ctrl+C は子にも届いているため。2 回目の Ctrl+C では、子も止めて
  から止まる(親のいない子を残さない)。入口は SIGINT を子に送り直さない
  (端末の Ctrl+C では子が 2 回受けて、後始末が途中で切れるため)。Windows
  以外で入口のプロセスだけに送った SIGINT は子に届かないので、無人で
  打ち切るときはプロセスグループに送る。子は、0.25 秒ごとに待ち直す
  (Windows の `wait()` は、時間を決めないと Ctrl+C で割り込めないため)
- setup に使える Python は 3.11 から 3.14。3.15 以降には onnxruntime の
  配布物がまだ無いので、何もせずに止まり、使う版の起動のしかたを示す
- 依存には、版の下限と、大きな版(major)で壊れたことのあるものの上限
  だけを書き、版を固定した一覧(lock)は持たない。OS と Python の版ごとに
  配布物が違い、保つ手間が大きいため。新しい版で壊れたことには、CI の
  週 1 回の実行で気づく。公開リポジトリでは、60 日間動きが無いと、GitHub
  が週 1 回の実行を止める(Actions の画面で有効に戻す)。失敗の知らせは、
  cron の行を最後に変えた人に届く
- 入口は、子のプロセスに自分の呼び方を環境変数 `CF_ENTRY` で渡す。道具の
  文面が案内するコマンドは、それを使う(`ctxf` は PATH に無いことが
  多いため)

## まだ無いもの

- MCP サーバーで、作業フォルダの設定が指す、作業フォルダの外のフォルダ
  (source のルート、モデルのフォルダ、用語の対応表)を読まないように
  すること。外のルートと手で置いたモデルは意図した機能なので、閉じるか
  どうか(閉じるなら、許す方法)は、まだ決めていない。`[embedding] model`
  に、テスト用の埋め込み(`hash-256-test-only`)も書ける

  あること)や、どの passage にも質問の識別子が無いことを知らせること。
  識別子の使われている場所をすべて挙げるのは、今は grep の仕事
- エージェントへの指示(始めの 1 文と道具の説明)で、検索の語に利用者の
  言葉(日本語)も残すよう書くこと。今は「英語で」と書いていて、日本語の
  設計文書の順位が下がりやすい。どちらも、計測した形を変えることになる
  ので、測り直しと合わせて行う

  セッションが要る)
