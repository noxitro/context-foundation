# 本番で使う

チームや自分の日々の作業で、この道具を Copilot CLI から使うときに、決める
こと・用意すること・運用することを、1 か所にまとめます。手順の細部は
[copilot.md](copilot.md)(入れ方と使い方)にあり、ここからはそこへ案内
します。数字の出どころは [benchmarks.md](benchmarks.md) です。

確度の表記: 【実測】手元で測った / 【未確認】確かめていない。

## 1. 使うかどうかを決める

この道具は、エージェントが「識別子が分からないまま、場所を探す」ときの
検索を足すものです。判定の決まりは、「回答の品質を grep だけの手順より
落とさないことを厳守し、そのうえで時間とトークン(費用)に得があるかを
見る」です。公開されている C++ のゲームエンジン 2 つで、grep とファイルを
読む道具だけのエージェントと比べた結果は次のとおりです(Copilot CLI、
Claude Haiku 5.5、評価用の質問を 3 回ずつ。回答は事前に決めた答えの要点で
AI が採点)【実測】。

| エンジン | 版 | 回答の合格率(この道具 / grep だけ) | 時間の中央値 | 費用の中央値 |
| --- | --- | --- | --- | --- |
| Godot(29 問) | 0.3 | 93.1% / 88.5%(点検後の要点) | 35% 減 | 32% 減 |
| O3DE(27 問) | 0.4.8 | 95.1% / 90.1% | 4% 減 | 3% 減(合計 7% 減) |

- どちらのエンジンでも、回答の品質は grep だけを下回らない
- 時間と費用の得は、エンジンで違う。Godot では 3 割ほど減った。O3DE では
  数 % にとどまる。O3DE で 0.4.7 の形を測ったときは 3 割ほど減ったが、
  検索の passage だけで答えて、近くにある関連の処理(別の版、呼び出し元、
  次の手順)を落とし、合格率が 77.8% に下がった。0.4.8 では関連の処理を
  見てから答えるように直し、品質を取り戻す代わりに、得の大部分を返した
  (下の「7. 品質を落とさないために」)
- Godot は 0.4.8 で測り直していない【未確認】。0.4.8 は、答える前に読む
  ものが増える向きの直しなので、Godot でも得が小さくなっている
  かもしれない【推測】
- 公開のエンジンは、モデルが識別子を一部覚えているので、grep だけの
  手順に有利な題材。数千万行の非公開のコードのように、grep では足場が
  見つかりにくいコードで差がどう変わるかは、このリポジトリでは測らない

効きやすいもの:

- 別のエンジンの用語や、日本語の自然文で、該当する処理を探す
- 設計文書からその実装を、コードから説明している文書を探す
- 大きいコードベースで、まず当たりを付ける(1 回の検索は 0.2 秒以下。
  約 24.5 万 passage の索引でも p95 で 0.23 秒)【実測】

向かないもの:

- 識別子が分かっていて、使われている場所をすべて挙げたい(この関数は
  どこから呼ばれているか)。grep か、cxxref のような参照の索引を使う。
  検索は上位の passage しか返さず、漏れを知らせない
- 時間と費用を大きく減らすことだけが目的の導入。公開のエンジンでは、
  品質を保った形での得は、数 % から 3 割ほどまで幅がある

判断の目安: 品質は、公開のエンジン 2 つで grep だけを下回らないことを
確かめてあります。時間と費用の得はコードベースで変わるので、得を
当てにするなら、導入の前に、自分たちの質問で grep だけと比べてください
([comparison-runbook.md](comparison-runbook.md))。

## 3. 入れる

個人で入れるなら、Copilot CLI のセッションで次の 3 行です。続けて、
新しいセッションで `/context-setup`(用意)を打ちます。

```text
/plugin marketplace add noxitro/context-foundation
/plugin install context-foundation@context-foundation
/settings experimental on
```

チームに配るときは、版をそろえるために、チームの Marketplace に
コミットの sha で固定して載せます([copilot.md](copilot.md) の「チームの
Marketplace に載せる」)。固定しないと、`copilot plugin update` のたびに
GitHub の main の先頭を取ってきます。

- 更新は、[CHANGELOG.md](../CHANGELOG.md) の「更新のあとにすること」を
  読んでから行う。依存の一覧が変わった版では、利用者ごとに
  `/context-setup` のやり直しが要る
- 前の版に戻すときは、固定した sha を前のものに戻して更新する
- 動いている Copilot(アプリを含む)がプラグインのフォルダを使っていると、
  更新は「使用中」で失敗する。Copilot を閉じてからやり直す

## 4. 索引を作る

作業フォルダ(Copilot を起動するフォルダ)で `/context-index` と打つと、
直下のフォルダの一覧から、索引に入れるものを選べます。

決めること:

- **入れるフォルダ**: エンジンのソース、参考にするアプリ、設計文書。
  ビルドの出力・依存物・版管理のフォルダは、既定で除く。生成物と秘密を
  持ちやすい名前(`.env`、鍵など)も除く。ただし、ファイルの中に書かれた
  秘密は名前では分からないので入る
- **作業フォルダの外を入れるか**: 入れられるが、その絶対パス(利用者の
  名前を含むことがある)が検索の結果に出て、モデルに送られる。避けるなら、
  ルートを作業フォルダの中に置く
- **`.cf` の扱い**: 索引にはソースの本文の写しが入る。版管理に入れない
  (git には入らないようにしてある。Perforce では `.p4ignore` に足す)。
  取ってきたリポジトリに `.cf` が入っていたら、使わずに消して作り直す

時間の目安【実測】: 初めての索引は、約 8,000 ファイルで 30 分ほど(CPU)。
GPU(DirectML)を使うと大きく縮む(Godot の全体で 4,959 秒が 290 秒)。
2 回目からは、変わったファイルの分だけを分け直し、変わった passage の分
だけを埋め込む。

## 5. 索引を最新に保つ

索引は、作ったときの内容のままです。ソースを同期したら(`p4 sync`、
`git pull` など)、もう一度 `/context-index` を打つか、次の 1 行を流します。

```text
python -I "<プラグインのフォルダ>\ctxf.py" index --config "<作業フォルダ>" --quiet
```

- 同期のスクリプトがあるなら、その最後にこの 1 行を足すのが確か。毎日の
  決まった時刻に流すなら、タスク スケジューラに登録する(例は
  [copilot.md](copilot.md) の「索引を更新する」。登録して動かすところは
  未確認)【未確認】
- 古さは `status --check` で数えられる。検索の結果にも、索引の後に変わった
  ファイルには `[changed since index]`、消えたファイルには
  `[file no longer exists]` の印が付く。増えたファイルは、作り直すまで
  出ない
- 終了コードで、成功(0)、置き換えられなかった(1。検索中だった)、
  設定の誤りなど(2)、用意が済んでいない(4)を見分けられる。2 と 4 の
  ときは、前の索引がそのまま使える
- セッションを開いたまま流してよい。検索は、次の検索から新しい索引を使う

## 6. 日々の使い方

- 索引のある作業フォルダでセッションを始めると、hook が「探すときは、
  検索を grep より先に」とモデルに知らせ、モデルが検索の道具を呼ぶ。
  利用者が検索を指示する必要はない
- 索引の無い作業フォルダでは、道具を出さない(定義のトークンも送らない)。
  そのフォルダで索引を作ると、次の依頼から道具が出る
- 質問は日本語でよい。エージェントは、検索語を英語の語と識別子に言い換える
- 答えの根拠は `source:path:start-end` で示される。大事な答えは、その
  ファイルを開いて確かめる

## 7. 品質を落とさないために

0.4.8 では、検索の結果を「答え」ではなく「場所を探す起点」として
扱わせるために、次を入れてあります。O3DE の評価で、品質が grep だけを
下回らなくなった形です【実測】。

- 上位 3 件の passage に、同じファイルにあるほかの関数・クラス・マクロの
  名前を最大 8 個添える(`same file also has: ...`)。エージェントは、
  grep をしなくても、近くの関連の処理の名前が分かる
- 道具の説明・結果の最後の 1 文・始めの 1 文で、「答える前に関連の処理
  (別の版、呼び出し元、次の手順)を見る」「質問が名前をそのまま挙げて
  いれば、先に grep する」と促す

設定で変えられるもの:

- `[search] related`: 添える名前の数。既定は 8。0 にすると添えない。
  0 にすると、O3DE で品質の下がった 0.4.7 の出力に近づくので、品質を
  落とさないことが前提なら変えない
- `[[source]] exclude`: 実装の場所を探すのが主な使い方なら、テスト・
  サンプル・ベンチマークのフォルダを除く。O3DE の調整用の質問では、
  除いた索引のほうが合格が多く、費用も少なかった(評価用の 0.4.8 の数字は、
  除いた索引のもの)【実測】。テストの書き方を探す使い方なら、除かない

```toml
[[source]]
id = "engine"
root = 'D:\work\engine\Source'
exclude = ['**/Tests/**', '**/Test/**', '**/Mocks/**', '**/Samples/**', '**/Benchmarks/**']
```

運用で守ること:

- 呼び出し元をすべて挙げる作業は、検索ではなく grep か参照の索引で行う。
  検索は上位の passage しか返さず、漏れを知らせない
- モデルを変えるときは、品質を確かめ直す。確かめたのは Claude Haiku 5.5
  だけ【未確認】
- 道具の説明と始めの 1 文を、自分たちで書き換えない。短くすると、
  ファイルを開かずに答える回が増える向きに働く(O3DE の 0.4.7)
- 導入の判断を自分たちの質問で行うなら、比べる質問と正解は公開の場所に
  置かない([comparison-runbook.md](comparison-runbook.md))

## 8. データと安全

- 索引づくりと埋め込みは、この PC の中で行う。この道具がソースの中身を
  外部に送ることはない。モデルの取得で送るのは、ファイルの名前だけ
- エージェントが読んだもの(質問、検索が返した passage、開いたファイル)は、
  エージェントが使うモデルの提供元に送られる。これは、この道具を使わない
  ときも同じ。非公開のコードで使う前に、どの提供元になら送ってよいかを
  決める
- MCP サーバーは読み取り専用。書き込みも、索引に無いファイルの読み出しも
  しない
- 秘密を持ちやすい名前のファイルは既定で除くが、秘密を見つける仕組みでは
  ない。秘密を置く場所は、索引に入れるフォルダから外す

## 9. うまく動かないとき

最初に、作業フォルダで次の 1 行を動かします。使っている Python、仮想環境、
モデルの有無、見えている索引を 1 回で出します。

```text
python -I "<プラグインのフォルダ>\ctxf.py" where
```

症状ごとの直し方は [copilot.md](copilot.md) の「うまく動かないとき」に
表でまとめています。よくあるもの:

- 検索の道具が出ない: `python` が PATH に無い、用意が済んでいない、用意の
  後に新しいセッションを始めていない
- 「Fell back to keyword」: 埋め込みモデルが無い(`/context-setup` で取る)
- 用意(setup)が pip で失敗する: 長いパス(`CF_HOME` を短いフォルダに)、
  プロキシ(`HTTPS_PROXY`)

## 10. 外す

1. `copilot plugin uninstall context-foundation`
2. `copilot plugin marketplace remove context-foundation`
3. 利用者ごとの置き場を消す(Windows なら `%LOCALAPPDATA%\context-foundation`)
4. 各作業フォルダの `.cf` を消す(索引にはソースの本文の写しが入っている)

## 11. 本番の前に、自分の環境で確かめること

このリポジトリでは、次を確かめていません【未確認】。本番で頼る前に、
自分の環境で一度確かめてください。

- GitHub Copilot のデスクトップアプリでの動作(作業フォルダが MCP サーバーに
  渡るか、拡張の結果が表示されるか)
- Linux と macOS でのプラグインとしての動作
- Claude Haiku 5.5 のほかのモデルでの、検索の使われ方と品質
- タスク スケジューラでの、索引の定期の更新
- ネットワークの共有フォルダ(UNC)の上の作業フォルダ
