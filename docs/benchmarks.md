# 計測の一覧

この道具について、何を測ったか、数字がどこにあるか、何をまだ測って
いないかを、1 か所にまとめます。数字の表そのものは、それぞれの文書に
あります。ここには、条件と主な値だけを写しています。食い違っていたら、
リンク先の文書が正です。

確度の表記: 【実測】手元で測った / 【未確認】確かめていない。

## 先に結論

- 測ったのは、部品ごとの性質です。索引づくりの時間と大きさ、検索 1 回の
  時間、当たりの割合、Copilot CLI で仕組みが通ること【実測】
- 当たりの評価と、既存の手順との比較の題材は、公開されているコード
  (O3DE と Godot)と、合成のコーパス(`tests/fixtures`)だけです。索引
  づくりと検索の時間は、公開されていない大きいエンジンのコードの一部
  (245,457 passage)でも測りました(下の「共通の条件」)
- 行の範囲で正解を付けた評価は、公開されているコード 2 つで行いました。
  検索だけの手法(既定の hybrid)で、上位 5 件に根拠が入った質問は、O3DE の
  評価例([examples/o3de](../examples/o3de/README.md))で 54%、Godot で
  50.0% です。どちらも、目安の 80% に届いていません。検索時間は、目安の
  内側です【実測】
- Godot の同じ質問で、既存の手順(grep だけ)と、この道具を足した手順を
  3 回ずつ比べました。回答の合格率は 79.3% と 78.2%、時間と費用の中央値は
  ほぼ同じで、差は出ていません。この道具を足した手順で、検索の結果が
  返ったのは 87 回のうち 42 回でした【実測。採点は AI】
- O3DE の評価例でも、同じ比較を 3 回ずつ行いました。回答の合格率は、
  既存の手順が 95.1%、この道具を足した手順が 87.7% で、どちらも目安の
  80% を超えています。この道具を足した手順は、合格が 81 回のうち 6 回
  少なく、時間の中央値は 9% 長く、費用の中央値は 8% 安い、という結果
  でした。検索の結果が返ったのは、81 回のうち 61 回です【実測。採点は
  AI】
- 事前に決めた目安では、候補の 2 つ(`hybrid` と `agent_cf`)は、Godot でも
  O3DE でも不合格です。O3DE では、既存の手順が、回答の合格率の目安を
  すでに満たしています。使う人自身のコーパス(実コーパス)での比較は、
  行っていません
- そのあと、エージェントへの出し方を、skill から「MCP サーバーと、検索を
  先に使うように促す始めの 1 文」に変えました(0.3)。Godot の評価用の
  29 問を 3 回ずつ、既存の手順と比べ直すと、回答の合格率は 75.9% と
  74.7% でほぼ同じ、時間の中央値は 35%、費用の中央値は 32% の減でした。
  「既存の手順より品質を下げず、時間か費用が 20% 以上下がる」という目安
  には、届きました【実測。採点は AI】
- 回答の合格率は、事前に決めた答えの要点では、目安の 80% に届いて
  いません。既存の手順も同じです。検索だけの手法の上位 5 件(50.0%)も、
  届いていないままです
- どちらの手法でも毎回不合格の質問が 3 問あったので、結果を見ていない
  点検役に、全問の答えの要点が「質問が聞いている内容か」を点検させ
  ました。点検後の要点では、回答の合格率は 93.1% と 88.5% で、どちらも
  80% を超えます。この数字では、0.3 の形は、エージェントの手法としての
  目安をすべて満たします。ただし、結果を見たあとの点検で、点検役も AI
  です。事前に決めた要点での結果は、上のとおり変わりません【実測】
- Godot での判定には、点検後の数字を採ります(2026-11-17 に、この道具の
  持ち主が決めた)。判定は、「エージェントで使う 0.3 の形は、Godot では
  目安を満たした。検索だけの手法は、満たしていない」です。使う人自身の
  コーパスでの判定は、まだです

- エージェント: GitHub Copilot CLI 1.0.112。モデルは Claude Haiku 5.5

`agent_cf` で、検索(skill)が使われたか:

- skill が読まれたのは、87 回のうち 50 回(57%)。セッションの始めの
  1 文は、87 回とも出ていた
- 検索の結果が実際に返ったのは、87 回のうち 42 回(48%)。skill を読んだ
  50 回のうち、5 回は検索を実行しなかった

  1 度は間違えて、検索が失敗した。skill の文が、入口を「この文書の

  2 回は返らないままだった。この書き方は直した(下の「skill の入口を

- 質問ごとに見ると、3 回とも skill を読んだ質問が 9、読んだり読まな

- 検索の結果が返った回のうち、答えのある質問の 33 回では、最初に返った

  質問の文のまま hybrid で検索したときは、21 問中 10 問だった。
  エージェントは検索語を言い換えている

回答の採点:

- 採点したのは AI です。基準は、評価の仕様の既定(答えの要点のうち、
  回答が正しく示した割合。0.8 以上が合格)で、回答を読む前に文書にした
- 手法・回・質問の番号を伏せて順番を混ぜ、独立した 2 つの採点役(Claude
  Sonnet)が全部を採点した。点が一致したのは 174 件中 169 件、合否が
  一致したのは 170 件(κ 0.93)
- 食い違った 5 件は、別の AI が基準に照らして決めた。決め方を変えても、
  合格は `agent_grep` で 68〜69 回、`agent_cf` で 66〜69 回の範囲に収まる
- 要点が 2 つか 3 つの質問では、1 つ欠けると不合格になる。平均の点は
  0.925 と 0.895

#### 答えの要点の点検(結果を見たあと)

上の比較で、どちらの手法でも 6 回とも不合格の質問が 3 問ありました。

点検役に、すべての質問の要点を点検させました。

手順(点検の前に決めて、書き残したもの):

- 点検役は、独立した 2 つの AI。回答・結果・どの質問が落ちたかは、
  見せない。見せるのは、答えのある 33 問の、質問と答えの要点(87 個)

- 要点ごとに、「質問が聞いている(正しく漏れのない回答なら、必ず述べる)」

  例を書くと、点検役を特定の質問へ寄せてしまうため)
- 2 つの点検役がどちらも「聞いていない」とした要点だけを外す
- 回答は採点し直さない。採点役がすでに付けた要点ごとの点から、残った
  要点の割合を出す。0.2 の形の比較と 0.3 の形の比較の、どの手法にも
  同じように当てる
- 事前に決めた要点での数字が、比較の結果である。出し直した数字は、

- 採点のしかたは、Godot のときと同じ。基準は同じ文書で、流す前に
