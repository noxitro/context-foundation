# 実コーパスで比べる手順

README の計画の手順 4(既存の手順と PoC を、同じ質問で比べて、続けるかを
決める)を、実際のコーパスで行うための手順書です。データの形式は
[evaluation-data-spec.md](evaluation-data-spec.md)(英語)が正です。

この手順で作るもの(質問、正解の注釈、結果、要約)は、どれもコーパスの
中身を含みます。手元の非公開の場所に置き、この公開リポジトリには
入れません。下のコマンドの例では、その場所を `<評価のフォルダ>` と
書いています。エージェントを使う手法(手順 5)を流すなら、作業フォルダの
外にします。エージェントは作業フォルダの中を読めるので、正解や前の回の
記録がそこにあると、答えを見て答えるおそれがあります。検索だけの手法
(手順 3)までなら、作業フォルダの `.cf` の下でも構いません。

質問と正解の書き方の実例は、公開のコーパスを題材にした
[examples/o3de](../examples/o3de/README.md) にあります。

下のコマンドの `ctxf <コマンド>` は、道具のコマンドの略です。`ctxf` という
名前のコマンドは、ふつうは PATH にありません。実際には
`python -I "<プラグインのフォルダ>\ctxf.py" <コマンド>` か、取得した
リポジトリの `.venv` の python で `ctxf.py --run <コマンド>` と動かします
([readme-ja.md](../readme-ja.md) の「コマンド」)。

## 0. 始める前に決めること

決めたことは、手順 6 で `runs.jsonl` に残します。走らせた後で変えると、
比較の意味が弱くなります。

| 決めること | 目安 |
| --- | --- |
| コーパスと、その版 | 1 つに絞る。コミットやチェンジリストの番号を控える |
| 判定の対象にする手法 | 既定は `hybrid` と `agent_cf`。0.3 からのプラグインの形(MCP サーバー)を判定するなら、`hybrid` と `agent_cf_mcp`(手順 7 の `--candidate` で渡す) |
| しきい値 | 仕様の「Decision thresholds」。変えるなら、走らせる前に |
| 回答の採点のしかた | 既定は、`expected_answer_points` のうち回答が示した割合(0〜1) |
| エージェントのモデルと、1 件あたりの時間の上限 | 全手法で同じにする |
| 作業フォルダの指示のファイル(`AGENTS.md` など)を読ませるか | 既定は読ませる。全手法で同じにする(手順 5) |
| 本文を送ってよいモデルの提供元 | 下の「データの扱い」 |

### データの扱い

この道具の検索そのものは、手元で完結します。エージェントを使う手法は
違います。質問、検索が返した passage、エージェントが開いたファイルは、
エージェントが使うモデルの提供元に送られます。

- Copilot の契約のモデルを使うと、GitHub の Copilot のサービスに送られる
- 自分のキーで使う設定(BYOK)にすると、その提供元の API に送られる
- アプリには、クラウドで動かすセッションがある。その場合は、作業フォルダの
  中身ごと、クラウドの環境に置かれる

非公開のコーパスでは、どの提供元になら送ってよいかを先に確かめ、決めた
ことを記録します。試しに流すのは、合成のコーパス(`tests/fixtures`)か、
公開されているコードにします。

## 1. 質問を作る

`cases.jsonl` に、1 行に 1 問を書きます。

1. 実際に困った場面から集める。「識別子が分からないまま探した」ことの
   ある人に、そのときの言い方のまま書いてもらう
2. 種類(`category`)ごとに 3 件以上(答えの無い質問は 2 件以上)を
   そろえる。数を多くするのは、この道具が狙う種類
   (`natural_language_only`・`doc_to_code`・`code_to_doc`)
3. 質問の言語(`question_language`)を書く。日本語と英語の両方で聞くなら、
   それぞれ 5 件以上
4. 正解の場所(`expected_evidence`)を、ファイルと行の範囲で書く。
   **どの手法も走らせる前に**書く。結果を見てから足したり削ったりしない
5. 正しい回答が示すべき事実(`expected_answer_points`)を、1〜3 個書く
6. 調整に使う質問を、別に 5〜10 件用意して `"split": "tune"` を付ける。
   除外の設定や順位の重みを直すときは、こちらだけを見る。判定に使う
   20〜30 件(`split` を書かないもの)の結果は、直す材料にしない

正解の場所の書き方:

- `source_id` は、設定の `[[source]]` の `id`。`path` は、その source の
  ルートからの相対パスを `/` 区切りで書く
- 行は 1 始まりで、両端を含む。答えの根拠になる範囲だけにする(ファイル
  全体にしない)
- 根拠が複数の場所に分かれるなら、複数書く。どれか 1 つが上位に出れば
  当たりと数え、いくつ見つかったかは別の指標(根拠の再現率)で見る
- レビューする人が正解と認める場所は、中心の 1 か所だけでなく、すべて書く
  (宣言と定義、プラットフォームやバックエンドごとの実装、長い関数の全体、
  答えがクラスならクラスの宣言)。書いていない場所は、正しい結果でも
  外れと数えられる。呼び出しているだけの場所、テスト、関係のある話題に
  触れているだけの場所は書かない。公開のコーパスの実例では、1 問に 3
  か所ずつ書いたときと、10 か所まで書いたときで、同じ検索結果の「上位
  5 件に当たり」が 0.05 から 0.55 に変わった。正解の広さで数字が変わる
  ので、比べるのは、同じ質問での手法どうしにする

書いたら、形式と、場所が実在するかを検査します。

```text
ctxf validate --cases <評価のフォルダ>\cases.jsonl --check-corpus
```

## 2. 索引を作る

`index.bat` か、`ctxf index --revision <版>` で作ります。版(コミットや
チェンジリストの番号)を渡すと、索引と評価の記録に残ります。終わったら
`ctxf status --format human` で、次を確かめます。

- 入ったファイルの数と、除いたファイルの数(理由ごと)。入るべきものが
  除かれていないか、生成物や外部のコードが入りすぎていないか
- 既定の名前(`build`・`packages` など)で除いたフォルダの中に、索引に
  入りうるファイルが多く無いか。入れるなら、そのフォルダを root にした
  `[[source]]` を足す
- 「構文で分ける言語のうち、解析できず行で分けた割合」。高いときは、
  マクロで文法が崩れている。その下に、行で分けた行が多いファイルが出る
  ので、開いて、原因のマクロを探す。`[chunk] attribute_macros` に、その
  名前(正規表現)を足すと下がることがある
- 作成にかかった時間と、索引の大きさ

設定を直したら、作り直します。直すときに見てよいのは、調整用の質問の
結果だけです。

## 3. 検索だけの手法を回す

費用はかかりません。`eval.bat` か、次のコマンドです。

```text
ctxf eval --cases <評価のフォルダ>\cases.jsonl ^
  --out <評価のフォルダ>\run-01 --corpus-revision <版>
```

`results.jsonl`・`runs.jsonl`・`summary.md`・`summary.json` ができます。
調整のときは `--split tune` を付けます。

## 4. 既存の手順を記録する

既存の手順は、「同じエージェント・同じモデル・同じ指示で、検索の道具だけを
外したもの」です(手法の名前は `agent_grep`)。記録するものは、仕様の
「What counts as retrieved evidence」のとおりです。

- 見つけた場所: エージェントが開いたファイルと行、回答で根拠に挙げた
  場所を、出てきた順に
- 回答、かかった時間、道具の呼び出しの数、トークン、費用
- 時間の上限を超えたら `timeout`、回答が出なかったら `gave_up`

Copilot CLI で回すなら、次の手順 5 の道具が、これを自動で記録します。
人の手で記録するときも、同じ形の `results.jsonl` に書けば、同じ要約に
並べられます。

## 5. エージェントを使う手法を回す

**費用がかかります。回数と見込みの費用を、流す前に利用者と確かめて
ください。** 道具は [bench](../bench/README.md) にあります。

手法ごとに、全部の質問を 3 回ずつ流します。

```text
python bench\agent_run.py --config <作業フォルダ> ^
  --cases <評価のフォルダ>\cases.jsonl --method agent_grep ^
  --out <評価のフォルダ>\agent-01 --run-id agent-01 --yes
python bench\agent_run.py --config <作業フォルダ> ^
  --cases <評価のフォルダ>\cases.jsonl --method agent_cf ^
  --out <評価のフォルダ>\agent-01 --run-id agent-01 --yes
```

- `<評価のフォルダ>` は、作業フォルダの外にする(この文書の初めの段落)。
  流したあとに、セッションの記録(`--out` の下の `homes` にある
  `events.jsonl`)で、道具の呼び出しとその結果に、質問・正解・結果の
  置き場が出てこないことを確かめる。公開されているコードでの計測では、
  作業フォルダの `.cf` の下に置いていたが、245 回のどの呼び出しにも
  出てこなかった([benchmarks.md](benchmarks.md))
- `agent_cf` は、この道具を置いたフォルダも、エージェントが読める場所
  として渡す。そこにも、質問・正解・結果を置かない。公開の評価例
  (`examples/o3de`)の質問で測るときは、評価例とテストを除いた写しから
  道具を動かす([bench の README](../bench/README.md) の「注意」)
- まず `--dry-run` で、実行されるコマンドを確かめる
- まず 1 問・1 回(`--case <id> --trials 1`)で、最後まで通るかを見る
- 止まっても、同じコマンドで続きから流せる(終わった回は飛ばす)
- 同じ時期に、手法を交互に流すのが望ましい。日によって、同じ質問でも
  トークンが 2〜3 割変わることがある(cxxref の計測での経験)
- cxxref の索引と比べるときは、`--method agent_grep_cxxref --cxxref
  <cxxref のフォルダ>` を足す(作業フォルダに cxxref の索引が要る)
- 0.3 からのプラグインの形(MCP サーバーと、検索を先に使うように促す始めの
  1 文)は、`--method agent_cf_mcp`。`agent_cf` は、0.2 までの skill の形
- 作業フォルダか、その版管理のルートまでに、指示のファイル(`AGENTS.md`・
  `CLAUDE.md`・`.github/copilot-instructions.md` など)があると、Copilot
  CLI は、それを毎回読む。中身は、どの手法の入力にも入る。道具は、見つけた
  ものを実行の前に知らせて、記録に残す。読ませる(実際の使い方に近い)か、
  読ませない(`--no-custom-instructions`)かを、走らせる前に決めて、全部の
  手法で同じにする
- この道具を置いたフォルダに指示のファイルがあると、`agent_cf` にだけ混ざる
  おそれがある(このフォルダを渡すのは `agent_cf` だけのため)。知らせに
  `tool:` と出たら、`--no-custom-instructions` を付けるか、そのファイルを
  外してから流す

回数の見積もり: 質問 25 件 × 3 回 × 手法 2 つで 150 回です。合成の
コーパスでの試し(Claude Haiku 5.5、1 回あたり入力 4 万トークン前後)では、
1 回 0.002〜0.004 ドルでした。実コーパスでは、読む量が増えるので、これより
多くなります。先に数問で測ってから、全体を見積もってください。

## 6. 回答を採点する

エージェントの結果の `answer_correctness` は、空のまま書き出されます。
走らせる前に決めた採点のしかたで、人が埋めます。

- 既定: `expected_answer_points` のうち、回答が正しく示した割合(0〜1)。
  0.8 以上を合格とする
- 答えの無い質問は、「コーパスに無い」と答えていれば 1、無いものを
  あるように答えていれば 0
- どの手法の回答かを伏せて採点すると、偏りが減る

## 7. 要約を作って、判定する

検索だけの手法の結果に、エージェントの結果を取り込んで、1 つの要約に
します。

```text
ctxf eval --cases <評価のフォルダ>\cases.jsonl ^
  --out <評価のフォルダ>\summary-01 ^
  --import <評価のフォルダ>\agent-01\results.jsonl ^
  --import-runs <評価のフォルダ>\agent-01\runs.jsonl ^
  --candidate hybrid,agent_cf
```

`summary.md` の「しきい値の合否」を見ます。判定に使うのは、対象の列に
印の付いた手法(走らせる前に決めたもの)だけです。

| 条件 | 見るところ |
| --- | --- |
| 上位 5 件に根拠の passage がある質問が 80% 以上 | 手法ごとの指標の hit@5 |
| 回答の合格率が 80% 以上 | エージェントを使う手法の表 |
| 検索時間の p95 が 3 秒以下 | 手法ごとの指標の p95 |
| 既存の手順より品質を下げず、時間か費用の中央値が 20% 以上下がる | しきい値の合否の「既存の手順との相対」 |

既存の手順が、すでに絶対の条件(上の 1〜3 行目)を満たしているときは、
同じ条件を満たすだけでは続ける理由になりません。相対の条件を満たすか、
既存の手順がしきい値に届かない種類を、ほかの種類を下げずに引き上げて
いるかで決めます。要約に、その旨と、引き上げた種類が出ます。

あわせて見るもの:

- 種類ごと・質問の言語ごとの内訳。全体では良くても、狙った種類
  (日本語の質問で英語のコードを探す、など)で効いていなければ、続ける
  理由は弱い
- 道具の出力の大きさと、退かされた結果の数。Copilot CLI は、大きすぎる
  道具の結果をモデルに渡さず、ファイルに退かせる。既存の手順の grep の
  結果でも起きる
- 索引の作成にかかった時間と大きさ。最初の索引づくりの時間と、ソースが
  変わったときの差分更新の時間(変わった passage の分だけ埋め込み直す)を
  分けて記録する

20〜30 件の質問では、統計として言い切れる差にはなりません。この判定は、
続けるかを決めるための最初の目安です。
